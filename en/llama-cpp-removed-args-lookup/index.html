"error: invalid argument" in llama.cpp: which build removed each llama-server and llama-cli option

error: invalid argument: --name means that the binary you ran has no such option in that build: it was removed, renamed, or it belongs to another llama.cpp tool. As of b12484 (2026-11-17), 50 option names that llama.cpp accepted at some point since b3716 are gone, 8 more only answer "the argument has been removed", and 22 still exist but llama-cli no longer takes them. Common cases: --mlock, --mmap, --no-mmap and --direct-io were removed in b10875 (2026-09-09) in favor of --load-mode; --defrag-thold was removed in b12347 (2026-11-12) and needs no replacement; -cnv and -no-cnv left llama-cli in b10584 (2026-08-22) and live on in llama-completion.

Which build removed my option?

Paste the command line, or the error. Each option is checked against the newest build for the binary in the text. Add your build number, or your Ollama release, to see whether your own build has it.

llama-server --version prints the build number: version: 10091 (commit) on older builds, version: ... (build 12465, commit ...) on current ones. The lookup runs in your browser on the data of this page; an Ollama release is translated to its bundled build with the table of the GGUF lookup. A name written with underscores after two dashes (--ctx_size) is read as --ctx-size, as llama.cpp itself does.

What happens to removed LLAMA_ARG_ environment variables?

Nothing, and that is the trap: llama.cpp reads only the variables of options it still has, so a removed variable is ignored without an error or a warning. 38 variables stopped being read this way. Two are different: LLAMA_ARG_DRAFT_MAX and LLAMA_ARG_DRAFT_MIN still belong to stub options, so since b8955 (2026-04-28) setting them stops startup with error while handling environment variable. From b7376 (2025-12-12), an option that has a negated form also reads LLAMA_ARG_NO_... next to its LLAMA_ARG_... variable.

Ollama: "llama-server process has terminated ... invalid argument"

Ollama starts a bundled llama-server with options it chooses, so this error means the server binary and the Ollama program are from different releases. Up to v0.32.5, Ollama's llm/llama_server.go passes --no-mmap and the release bundles llama.cpp b10091. From v0.32.6 it passes --load-mode and bundles b10242; --load-mode exists from b10105 (2026-07-23). invalid argument: --load-mode therefore comes from a llama-server older than b10105 started by an Ollama of v0.32.6 or newer. Reinstall so that both come from one release. The build inside every Ollama release is listed in the GGUF lookup.

How was this built?

  • Options: common/arg.cpp at each of the 391 commits that changed it, from the commit that created it (b3716 (2024-09-09)) to b12484 (2026-11-17). Every add_opt(common_arg(...)) gives the names, the negated names, set_examples / set_excludes (which tools register it) and set_env.
  • Builds: each commit is mapped to the first bNNNN tag that contains it (7,887 tags). Dates are UTC dates of the tagged commit.
  • Binaries: llama-server parses with LLAMA_EXAMPLE_SERVER; llama-cli with LLAMA_EXAMPLE_MAIN before b7348 and LLAMA_EXAMPLE_CLI from it; llama-completion with LLAMA_EXAMPLE_COMPLETION. An option without set_examples, or tagged LLAMA_EXAMPLE_COMMON, belongs to all three.
  • Check: a second script searched the file at the build tags themselves for each quoted name, at the build where the data says it appeared or disappeared and at the build before: all 50 removals, the stubs, the removed variables and 60 additions agree.
  • Ollama: llm/llama_server.go at the tags v0.32.5 and v0.32.6, and the bundled build of each release from the GGUF lookup's data.

What this page does not cover

  • Nothing was compiled or run. The page says which names the parser registers, not whether an option still has an effect.
  • Options that changed meaning or default without changing name are not listed.
  • The lookup answers for llama-server, llama-cli and llama-completion. For the other tools that use the same table, the data file lists which tools each option is registered for. llama-bench parses its options itself and is not covered.
  • Before b3716 the ranges are coarse, and options that came and went between two of the builds read are missing.
  • Forks and wrappers (llama-cpp-python, LM Studio, koboldcpp) have their own option names.

Questions

What does "error: invalid argument: --mlock" mean in llama.cpp?
The llama-server or llama-cli you ran does not have that option. --mlock, --mmap, --no-mmap and --direct-io were removed in build b10875 (2026-09-09). Use --load-mode instead: --load-mode mlock, mmap, mmap+mlock, none or dio. --load-mode exists from b10105 (2026-07-23).
Why does llama-cli say invalid argument for -cnv or -no-cnv?
llama-cli was replaced by a new chat program in build b7348 (2025-12-10), and -cnv / -no-cnv left it in b10584 (2026-08-22). The previous program is still built as llama-completion, which accepts both.
Is --defrag-thold still needed?
No. Its last warning said it is "deprecated and no longer necessary to specify", and build b12347 (2026-11-12) removed it. Delete it from the command line.
What happens to a removed LLAMA_ARG_ environment variable?
Nothing: llama.cpp reads only the variables of options it still has, so a removed one is ignored without an error or a warning. The exceptions are LLAMA_ARG_DRAFT_MAX and LLAMA_ARG_DRAFT_MIN, which stop startup since b8955 (2026-04-28) with "the argument has been removed".
Why does Ollama say "llama-server process has terminated ... invalid argument: --load-mode"?
The llama-server that Ollama started is older than b10105, the first build with --load-mode. Ollama passes --load-mode from v0.32.6, which bundles llama.cpp b10242; v0.32.5 passes --no-mmap and bundles b10091. The program and the bundled server are from different installs: reinstall Ollama so that both come from one release.
What is the difference between "invalid argument" and "unknown argument"?
The wording. Builds before b3716 (2024-09-09) parsed options by hand and printed "error: unknown argument: NAME"; from that build the options live in one table (common/arg.cpp) and the message is "error: invalid argument: NAME".
