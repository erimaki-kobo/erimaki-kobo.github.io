Answers for LLM inference engineers

Do I need to redownload my GGUF? Check which upload you have and what changed

Redownload only if the tensors changed. If a re-upload changed only metadata (usually the chat template), patch your copy with gguf-new-metadata instead. The check below lists every upload of a file on the Hugging Face Hub, finds yours by sha256 or by reading its header, and compares the two files directly: metadata keys, tensor names, types and shapes, and sampled tensor bytes. In the 68 re-uploads we checked across 23 popular repositories, 28 changed only metadata (17 of them only the chat template), 25 re-quantized the same tensors, 13 added, removed or re-typed tensors, and in 2 we found no difference in the metadata or the sampled bytes.

Where your copy came fromHow to get the sha256

The Hugging Face registry serves the GGUF file as that blob, so the hash is the file's sha256 (we checked: the registry's model layer for bartowski/Meta-Llama-3.1-8B-Instruct-GGUF:Q4_K_M has the sha256 of the newest Q4_K_M.gguf). Or type the tag in the tool to see what a new pull would get.

How do I patch a metadata-only change?

When the tool says "metadata only", it prints the command. The tools come with pip install gguf:

Changed keyCommand
tokenizer.chat_templategguf-new-metadata old.gguf fixed.gguf --chat-template-file chat_template.jinja (the tool can download the new template)
tokenizer.ggml.pre--pre-tokenizer NAME (see the pre-tokenizer lookup)
tokenizer.ggml.bos_token_id, eos_token_id, ...--special-token-by-id eos 106
general.name, general.description--general-name, --general-description
a key that was removed--remove-metadata KEY
a number or a boolean, e.g. tokenizer.ggml.add_bos_tokengguf-set-metadata fixed.gguf KEY VALUE (in place). For False pass an empty string, '': the text false becomes True, because the value goes through numpy's bool. We hit this with gguf 0.19.0.

Other changed keys (a new array, a new architecture parameter) cannot be set with these tools; redownload, or keep your file if the key does not matter to you. A patched file has the same metadata as the new upload but a different sha256, because the keys are written in another order; pick it in the tool to confirm that nothing else differs. We tested the round trip on small generated GGUF files: after patching, the header comparison showed no difference.

How does the check work?

  • History: POST /api/models/REPO/paths-info/REV gives the file's sha256 and the last commit that changed it; asking again at that commit's parent gives the upload before, and so on. One request per upload.
  • Headers: HTTP range requests on /resolve/COMMIT/FILE, parsed in the page (GGUF versions 2 and 3): every metadata key, and every tensor's name, type, shape and offset. Arrays such as the vocabulary are compared by a hash of their bytes.
  • Tensor bytes: when the tensors have the same names, types and shapes, the first 4 KiB of 16 tensors (always the first and the last) are compared, each at its own offset. This catches re-quantization, but it is a sample: a change outside the sampled bytes shows as "no visible change".
  • Your file: a sha256 is matched against the uploads' sha256; a picked file is matched by its header bytes and its size.

What it does not do

  • Gated and private repositories (the page has no Hugging Face login).
  • Split files (-00001-of-0000N): it checks the part you pick; the header is in the first part.
  • Renamed files: a new file name has its own history. Repositories whose history was squashed show only the uploads that remain.
  • It does not say whether a new upload is better, only what changed.

Questions

Why do GGUF files on Hugging Face get re-uploaded?
Most often to fix the chat template or tokenizer settings after a llama.cpp fix, and sometimes to re-quantize with a new importance matrix or after a conversion bug. In the 68 re-uploads we checked, 28 changed only metadata, 25 changed tensor data with the same layout and 13 changed the tensors themselves.
How do I find the sha256 of my GGUF?
Hugging Face cache: the file name under blobs/ is the sha256. Ollama: ollama show --modelfile prints FROM .../blobs/sha256-<hash>. Any other copy: sha256sum model.gguf. Or pick the file in the tool, which compares its header without hashing it.
Can I fix a chat template without downloading the GGUF again?
Yes, when only metadata changed. gguf-new-metadata (pip install gguf) writes a copy with a new chat template, pre-tokenizer, special token ids, name or description; gguf-set-metadata changes a number or a boolean in place.
Does Ollama update a model pulled from hf.co automatically?
No. ollama pull hf.co/<repo>:<quant> again fetches the current file; until then Ollama keeps the blob it downloaded.
Why does gguf-set-metadata set my boolean to True when I type false?
It converts the text with numpy's bool, and any non-empty string is True. Pass an empty string ('') to set False. Checked with gguf 0.19.0.
