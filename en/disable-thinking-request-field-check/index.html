How to turn thinking off per request on Ollama, llama-server, vLLM and SGLang, and check that it worked

There is no field that works everywhere, and every one of these servers drops a field it does not know without an error. On Ollama's /v1/chat/completions only "reasoning_effort": "none" works (0.12.4 and later). think and chat_template_kwargs are silently dropped there. On llama-server, vLLM and SGLang, "chat_template_kwargs": {"enable_thinking": false} works for Qwen3-style templates. "reasoning_effort": "none" works only from llama.cpp b10121, vLLM v0.22.0 and SGLang v0.5.10. Older vLLM is the worst case: v0.18.0–v0.21.x accept "none" and keep thinking. Sampling fields fail the same quiet way: Ollama's OpenAI endpoint drops top_k, min_p and repeat_penalty. vLLM and SGLang spell the penalty repetition_penalty and ignore llama.cpp's repeat_penalty. thinkcheck.py sends paired requests to your own server and tells you which fields worked, which were ignored and which were rejected.

Model limits come first: Qwen3-2507 “Thinking” and Qwen3-VL “Thinking” templates always open a think block, so no field turns them off; use the matching Instruct model. GPT-OSS cannot stop reasoning either: Ollama maps "none" to "low" for it, per its OpenAI compatibility page. SGLang v0.5.23 also accepts a top-level "thinking": {"type": "disabled"}, which sets both thinking and enable_thinking in the template arguments unless the request sets them. The /no_think suffix is a prompt convention of the original Qwen3 hybrid models, not a server feature: the model may or may not follow it.

Why the string "false" fails

Qwen3's template tests enable_thinking is defined and enable_thinking is false. The string "false" is defined but is not false, so the template takes the thinking branch. We rendered the template through /apply-template on three llama-server builds with a toy model that carries the real Qwen3 template. b6393 returned the thinking prompt for the string. b10108 and b12809 return HTTP 400 invalid type for "enable_thinking" (expected boolean, got string). vLLM and SGLang pass the value to Jinja as it is, so a string there silently keeps thinking on. This bites clients that build JSON by hand or from environment variables.

Why vLLM v0.18–v0.21 keep thinking with reasoning_effort: "none"

vLLM v0.18.0 added "none" to the allowed values (PR #36238) but passed it to the chat template only as the variable reasoning_effort. Qwen3 templates never read that variable, so the model thought as usual and the request still returned 200. v0.22.0 (PR #43401) also sets enable_thinking to reasoning_effort != "none", unless the request already sets enable_thinking in chat_template_kwargs. If you cannot upgrade, send the chat_template_kwargs form; it works on every version since v0.5.1.

Which sampling fields are silently ignored?

Ollama's /v1/chat/completions ignores top_k, min_p and both repetition-penalty spellings. Each of the other three servers ignores the repetition-penalty spelling of the others. None of the four rejects a field it does not know.

Ollama's OpenAI handler copies only temperature, top_p, seed, stop, max_tokens, frequency_penalty, presence_penalty and response_format into the model options. Go's JSON decoder drops everything else. To set top_k, min_p or repeat_penalty on Ollama, call the native /api/chat with "options", or put PARAMETER lines in the Modelfile. In vLLM, run with VLLM_LOGGING_LEVEL=DEBUG to see the line “The following fields were present in the request but ignored”.

Where does the thinking come back, and does hiding it save tokens?

A client that reads the wrong field sees no thinking and concludes it is off while the server is still generating it. Check usage.completion_tokens, not only the text.

  • Ollama /v1: message.reasoning (since v0.11.0). The native API uses message.thinking.
  • llama-server: message.reasoning_content with the default --reasoning-format. With "reasoning_format": "none" the <think> block stays in content. We forced a think block with a grammar while sending enable_thinking: false; the server then left it in content, not in reasoning_content.
  • vLLM: message.reasoning. v0.12.0–v0.15.1 sent both reasoning and reasoning_content; v0.16.0 removed reasoning_content (PR #33402), and older clients that read only it see nothing. Without --reasoning-parser the think block stays in content.
  • SGLang: message.reasoning_content, only when the server runs with --reasoning-parser and the request keeps separate_reasoning: true.

Hiding is not stopping. vLLM's include_reasoning: false (v0.10.1+), SGLang's separate_reasoning: false and llama-server's reasoning_format: "none" only change the response. The tokens are still generated. To cap thinking without turning it off, use a budget. llama-server takes thinking_budget_tokens per request since b8287 and reasoning_budget_tokens since b9982, or --reasoning-budget at start-up. vLLM takes thinking_token_budget since v0.19.0; it needs a reasoning parser or --reasoning-config to know where thinking ends.

How do I check my own server?

curl -O https://erimaki-kobo.github.io/en/disable-thinking-request-field-check/thinkcheck.py
python thinkcheck.py --base-url http://localhost:11434/v1 --model qwen3:0.6b
python thinkcheck.py --base-url http://localhost:8000/v1 --model Qwen/Qwen3-0.6B --json result.json

It sends a baseline request, then the same request with each thinking switch, at temperature 0. A switch “worked” if the baseline thought and the switched request did not (it looks in reasoning_content, reasoning, reasoning_text and for a non-empty <think> block in content). For sampling it compares three samples at temperature 1.5 with and without top_k: 1 and min_p: 1.0. Identical samples mean the field worked; different samples mean it was dropped. It also repeats a seed, compares the three penalty spellings at temperature 0, and sends one unknown field to see whether the server is strict. About 24 short requests in total; it uses the first switch that worked in the sampling checks so thinking does not eat max_tokens. Use --extra '{"key": ...}' for fields your proxy needs and --api-key for a hosted endpoint.

Output against llama-server b12809 with the toy model (random weights, so it never thinks on its own and the thinking rows say “can't tell”; a toy over 151,936 tokens also never repeats, so the penalty rows show no effect):

How this was measured

  • llama-server: built from source on CPU at b6393, b10108 and b12809. make_toy_qwen3.py writes a 2-layer random-weight Qwen3 GGUF with the real Qwen2 vocabulary plus Qwen3's four added tokens and the real Qwen3-0.6B template, both from llama.cpp's models/ folder. render_matrix.py posts each request body to /apply-template, which uses the same request parsing as chat completions. A body “turns thinking off” when the rendered prompt ends with the empty <think></think> block. Results: results.jsonl (21 rows). run.sh repeats it for any build in a few minutes.
  • First versions: found by binary search over every release tag (8,832 llama.cpp tags, 226 vLLM, 168 SGLang, all Ollama releases), reading the request-parsing file at each tag. Dates are PyPI upload dates for vLLM and SGLang and tag commit dates for llama.cpp and Ollama.
  • Not run: Ollama, vLLM and SGLang were not started; their rows come from the request models and handlers at the tags named. LM Studio is closed source and not covered (see lmstudio-bug-tracker #1990 for enableThinking being ignored on its OpenAI endpoint).

FAQ

How do I disable thinking on Ollama's OpenAI-compatible endpoint?
Send "reasoning_effort": "none" (or "reasoning": {"effort": "none"}) on Ollama 0.12.4 or later. With the OpenAI Python client that is reasoning_effort="none"; no extra_body is needed. On the native API, send "think": false.
I set --default-chat-template-kwargs '{"thinking": false}' on vLLM and Qwen3 still thinks.
Qwen3 reads enable_thinking; thinking is the key for DeepSeek V3.1 and Kimi K2 templates. vLLM keeps only the keys the template reads (since v0.11.0) and drops the rest without a warning. A request-level chat_template_kwargs overrides the server default.
Why does vLLM keep thinking when I send reasoning_effort: "none"?
On v0.18.0–v0.21.x it reaches the template only as a variable that Qwen3 does not read. Upgrade to v0.22.0 or send chat_template_kwargs: {"enable_thinking": false}.
Does llama-server accept enable_thinking as a string?
No. Since b6394 the string returns HTTP 400; in b6393 and older it was accepted and the model kept thinking. Send a JSON boolean.
Are top_k and min_p ignored by Ollama's OpenAI API?
Yes, without an error. Use the native /api/chat with "options", or the Modelfile.
Does reasoning_effort: "low" shorten Qwen3's thinking?
No. Qwen3 templates have no effort levels; on llama-server, vLLM v0.22.0+ and SGLang a value other than "none" turns thinking on and nothing else. On Ollama, a non-thinking model returns 400 “does not support thinking” for such a value on /v1/chat/completions. Use a thinking budget to shorten it.
Does include_reasoning: false make responses faster?
No. It removes the reasoning from the response; the model still generates it.
Why does SGLang return the thinking inside content?
The server was started without --reasoning-parser, or the request sent separate_reasoning: false.

Limitations

  • Only llama-server was run, on a random-weight toy model. The rows for Ollama, vLLM and SGLang are read from the source; a real model run on those servers (ours or yours with thinkcheck.py) may show template-specific behaviour we did not see.
  • Streaming responses are not checked. Thinking can be parsed differently in delta chunks.
  • The table covers templates that read enable_thinking. Models with their own switch (GPT-OSS effort levels, DeepSeek V3.1 thinking, Gemma 4, which is off by default) need their own key.
  • The penalty check needs a model that repeats when asked to; on a model that never repeats, every spelling shows “no effect seen”.
