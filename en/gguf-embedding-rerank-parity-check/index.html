Answers for LLM inference engineers

Embeddings or rerank scores from llama.cpp or Ollama don't match sentence-transformers? Find the cause

A correct GGUF served by llama-server gives the same vectors as sentence-transformers. We measured a cosine of 1.000000 on F32 GGUFs. When the numbers differ, the engine is usually computing something else. It may pool differently, skip the query: prefix that sentence-transformers adds on its own, or read more tokens than the model's max_seq_length. For rerankers, the GGUF may have lost part of the model. BERT cross-encoders converted before llama.cpp b12818 have no pooler (#33109). Qwen3-Reranker GGUFs converted as a plain LLM have no head at all and return meaningless scores. embedcheck.py sends the same inputs to your server and to the original model, and names the cause.

Published 2026-11-28 · llama-server measured at b12826 (2026-11-27) on CPU, with GGUFs converted by b12826 and by b12816 (the last build before the pooler fix). The models were small random-weight checkpoints with the real BERT (bge) and Qwen2 vocabularies. References came from sentence-transformers 6.3.0 and transformers 5.24.1. Ollama v0.40.19, TEI v1.10.0 and vLLM v0.34.0 were read from source, not run · Tool version 1.0 (Python 3.9+, needs sentence-transformers and requests)

Exit status 0 means it matches (notes such as “not normalized” or “refused the long input” are printed but do not fail). Exit 1 means a mismatch, and 2 means the server could not be reached. --gguf also reads the GGUF header. It flags a missing pooling_type, a reranker with no cls.* tensors, a Qwen3 GGUF without rank pooling, and a BERT classifier without cls.weight (the dropped pooler). How close is close enough: F32/F16 GGUFs land above 0.999. Q8_0 usually lands above 0.99. Below that, with no pooling, prefix or truncation explanation, suspect the conversion.

Fixes

Pooling
Start llama-server with --pooling cls|mean|last matching the model's 1_Pooling/config.json. Or reconvert from the full model folder: convert_hf_to_gguf.py reads modules.json and 1_Pooling to set pooling_type, and a bare folder (only config.json and weights) gives a GGUF without one.
Prefix
Add the prefix to the text yourself: search_query: / search_document: for nomic-embed, query: / passage: for E5, the instruction for Qwen3-Embedding. Or tell sentence-transformers not to add it (prompt="") when you compare.
Truncation
Cut inputs to max_seq_length tokens before sending (all-MiniLM-L6-v2: 256, although its GGUF says 512). For llama-server, raise -ub and -b together to accept longer inputs up to the model's context.
Cross-encoder pooler
Reconvert BertForSequenceClassification checkpoints with llama.cpp b12818 or later (PR #33122, merged 2026-11-27). --gguf shows cls.weight and classifier.activation=tanh on a good one.
Qwen3-Reranker head
Convert from a folder whose README.md starts with # Qwen3-Reranker, or whose name contains qwen3-reranker (support since b6578, PR #15824). Check that the GGUF lists cls.output.weight and pooling_type rank. On vLLM, the original checkpoint needs --hf_overrides '{"architectures": ["Qwen3ForSequenceClassification"], "classifier_from_token": ["no", "yes"], "is_original_qwen3_reranker": true}' and the reranker chat template.
Quantized KV cache
Don't use -ctk q4_0 -ctv q4_0 for rerankers. In #16407 ggerganov advised against it for reranking, and against q8_0 too.

FAQ

Why are llama.cpp embeddings different from sentence-transformers?

On an F32 GGUF of the same model, llama-server reproduced sentence-transformers to a cosine of 1.000000 in our runs. When they differ, the cause is almost always one of four settings: a different pooling (the GGUF's pooling_type or a --pooling flag), a prompt prefix that sentence-transformers adds automatically from default_prompt_name, a different truncation length (sentence-transformers cuts at max_seq_length, llama.cpp does not), or quantization. embedcheck.py tells you which.

Why do Ollama embeddings not match Hugging Face cosine similarity?

Ollama's /api/embed and /v1/embeddings L2-normalize and truncate to the GGUF context_length (or num_ctx), not to the model's max_seq_length, and never add the model's query or document prefix. Texts longer than max_seq_length and models with a default prompt (E5-style "query: ") differ from sentence-transformers. The legacy /api/embeddings returns unnormalized vectors.

Why does llama-server /v1/rerank return wrong or tiny scores (like 4.5e-23)?

The GGUF has no classifier head. A Qwen3-Reranker converted as a plain Qwen3 model has no cls.output.weight and no rank pooling; llama-server then returns softmax over the last hidden state, which is tiny on a real model and changes with the other documents in the request. The converter treats Qwen3 as a reranker only if README.md contains '# Qwen3-Reranker', the folder or _name_or_path contains 'qwen3-reranker', or the architecture is *ForSequenceClassification.

Why does a cross-encoder GGUF rank documents differently from CrossEncoder.predict?

Until 2026-11-27 llama.cpp's converter dropped the BERT pooler (dense + tanh), so BertForSequenceClassification models such as cross-encoder/ms-marco-MiniLM-L-12-v2 scored the raw [CLS] vector (llama.cpp #33109). PR #33122 fixed the converter; the first build with it is b12818. Reconvert. Separately, llama.cpp still feeds token_type_ids = 0 for the document, so scores of segment-trained cross-encoders are still slightly off in b12826.

Is llama-server's rerank score a probability?

For Qwen3-Reranker GGUFs, yes: llama.cpp applies a softmax to the yes/no head, which equals P(yes) from the model card recipe (measured equal). For BERT cross-encoders it returns the raw logit; TEI and vLLM apply a sigmoid by default, so the numbers differ but the order is the same.
