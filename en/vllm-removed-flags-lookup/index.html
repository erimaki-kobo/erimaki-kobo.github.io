"unrecognized arguments" and settings that silently stop working: removed vLLM arguments, environment variables and request fields

vLLM has removed 81 command-line arguments, 120 environment variables and 11 server request fields since its first release. A removed argument stops vllm serve with "unrecognized arguments"; a removed variable or request field does not: vLLM ignores it and runs without the setting. Common cases: --speculative-model ended in v0.8.2 (use --speculative-config), --task in v0.12.0 (use --runner and --convert), VLLM_ATTENTION_BACKEND in v0.14.1 (use --attention-backend), and guided_json in v0.11.2 (use structured_outputs). Paste your command or request below to check every name in it.

Published 2026-11-13 · vLLM v0.1.0 to v0.33.0 (98 releases) · SGLang v0.1.3 to v0.5.23 (145 releases) · read from each release's source

Which removals fail loudly, and which fail silently?

Only command-line arguments and SamplingParams arguments raise an error. Environment variables and server request fields are dropped without one.

How was this built?

  • vLLM arguments: at each of 98 final releases, every name in add_argument(...) in vllm/engine/arg_utils.py and the server's cli_args.py (under entrypoints/openai/, then launchers/, then common/), plus fields of the FrontendArgs dataclasses that become arguments.
  • Environment variables: the keys of environment_variables in vllm/envs.py, 74 releases from v0.4.2.
  • Request fields: the fields of SamplingParams, ChatCompletionRequest and CompletionRequest at each release.
  • SGLang: add_argument(...) in server_args.py, and from v0.5.14 the annotated dataclass fields that generate arguments, 145 releases.
  • Replacements: read from the help text and source of the releases around each removal. Two are marked "probably": the move was not traced line by line.

What this page does not cover

  • Release candidates and code on the main branch. An argument added after v0.33.0 shows as "not in any release".
  • Values: an argument that still exists can change the values it accepts (for example a backend name). Only names are checked.
  • Variables read outside vllm/envs.py, SGLang's own SGLANG_ variables, and SGLang's request fields.
  • Which releases accept --no-X for each switch is summarized in the note above, not checked per argument by the lookup.

Questions

Why does vllm serve say "unrecognized arguments: --X"?
The argument is not defined in your vLLM release: either it was removed (for example --speculative-model after v0.8.2, --guided-decoding-backend after v0.10.2, --task after v0.12.0, --disable-log-requests after v0.16.0) or it was added in a newer release than yours. The lookup on this page gives the release range for every argument vLLM ever had.
Is VLLM_ATTENTION_BACKEND still supported?
No. It was last read in v0.14.1. From v0.13.0 the replacement is the --attention-backend argument. Setting the variable on newer releases does not raise an error; from v0.17.0 vLLM only logs "Unknown vLLM environment variable detected" at startup.
Why is my guided_json request not constrained any more?
guided_json and the other guided_* request fields were removed after v0.11.2. Because vLLM's server accepts unknown fields and drops them, the request still succeeds and the output is simply unconstrained. Use structured_outputs (from v0.11.0) or response_format. vLLM v0.30.0 and later log a warning for these specific fields.
How do I turn off a boolean option like chunked prefill?
From v0.8.5, vLLM's boolean options use --X and --no-X, so write --no-enable-chunked-prefill. The old form --enable-chunked-prefill False fails there with "unrecognized arguments: False". On v0.5.3 to v0.8.4 write --enable-chunked-prefill false.
Can I write --max_model_len with underscores?
Yes. vLLM's argument parser accepts underscores and dashes in argument names, and reads --json-arg.key value as a key inside a JSON argument.
