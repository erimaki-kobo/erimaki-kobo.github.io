ImportError: cannot import name 'X' from 'transformers': which releases have each name

The installed transformers release does not export that name: it is either older than the release that added it or newer than the last release that had it. The fix is to install a release inside the range that has the name, or to import the replacement. Paste the error below to get the range for any of the 5,893 names that from transformers import ... has resolved between 2.0.0 and 5.23.0: 4,134 import in 5.23.0, and 1,617 are gone (640 of them are the TensorFlow and Flax classes that 5.0.0 removed).

Two releases account for most of it: 5.0.0 dropped TensorFlow and Flax, and 4.41.0 deleted the per-model lists of checkpoint names. Why do BertTokenizerFast and ...ImageProcessorFast still import in 5.x?

Because the lazy module answers for them even though no list has them. From 5.0.0, _LazyModule.__getattr__ (utils/import_utils.py) resolves a missing name ending in TokenizerFast to the class without the suffix, and tries the table SLOW_TO_FAST_CONVERTERS for tokenizer names whose class was merged into another one. From 5.4.0 it does the same for names ending in ImageProcessorFast, with a deprecation warning. In 5.23.0, 47 names ending in TokenizerFast and 91 ending in ImageProcessorFast import this way, and the object you get is the class without the suffix. The lookup reports these as "imports", with the class that is returned. A ...TokenizerFast name whose model lost its tokenizer class altogether is not rescued and raises the ImportError.

What about transformers.utils and transformers.file_utils?

transformers.file_utils has been a compatibility shim since 4.18.0, and both modules lost their TensorFlow and Flax helpers in 5.0.0. Up to 4.17.0, file_utils.py held the helpers themselves; 4.18.0 moved them into transformers/utils/ and left a module that re-exports part of them, so 170 names stopped being importable from transformers.file_utils in that one release (most of them are in transformers.utils from then on). 82 names are left in 5.23.0. transformers.utils exists as a package from 3.1.0 and binds 280 names in 5.23.0; 5.0.0 removed 43 (the is_tf_available and is_flax_available families, TF2_WEIGHTS_NAME, FLAX_WEIGHTS_NAME and similar). Other packages often import private helpers from these two modules, which is why diffusers, sentence-transformers or a model's remote code can fail right after a transformers upgrade.

How do I read the error?

  • The module after "from" tells you which table to look in. from 'transformers' is the top level; from 'transformers.utils' and from 'transformers.file_utils' are the two helper modules this page also covers.
  • The path in parentheses is the copy of transformers that was imported. If the version there is not the one you thought you installed (a second environment, a user-site copy, a notebook kernel that was not restarted), fix that first: python -c "import transformers; print(transformers.__version__, transformers.__file__)".
  • The traceback tells you who asked for the name. If it is another package, upgrading that package is the lasting fix and pinning transformers is the quick one.
  • "(unknown location)" instead of a path, or an error that names a file in your own project, usually means a local file or folder called transformers shadows the library.
  • A name that does import but fails when used, with a message that asks you to install PyTorch, sentencepiece or another backend, is a different case: the name exists, its backend is missing.

How was this read, and how was it checked?

From the source of each release tag, with Python's ast module; no release was installed or imported.

  • 2.0.0 to 4.1.1: __init__.py imports everything eagerly, so the names are its from .module import ... statements.
  • 4.2.0 and later: the top level is a lazy module that serves the names listed in _import_structure. Those lists are read, without the utils.dummy_* placeholders.
  • 4.52.1 and later: __init__.py builds the model part of the lists with define_import_structure, from the __all__ of every file under models/. Those are read too.
  • 5.x: the three alias rules of _LazyModule.__getattr__ described above are applied; which rules a release has is read from that method's code, and the build stops if the method starts looking at name endings it did not look at before.
  • transformers.utils and transformers.file_utils: every name the module binds at module level.
  • Release dates and the list of yanked releases come from PyPI. Where the .0 release of a minor version was yanked (4.14, 4.25, 4.46, 4.52, 4.57, 5.10) the first release that pip installs is used.

Checks, all by a second reading rather than by running the library: (1) lazy releases keep a static copy of the lists for type checkers, the imports under if TYPE_CHECKING:; in all 80 lazy releases every name of that copy is in our reading, and 49 of them are identical (the rest have up to 26 runtime names that upstream forgot to mirror; those do import). (2) __all__ was read a second time line by line, the way the library's own fetch__all__ does, for 4,932 model files of three releases, with no difference. (3) 19 known facts from release notes and forum threads (for example AdamW gone in 4.50.0, LlamaTokenizer new in 4.28.0, TF classes gone in 5.0.0) all hold.

Limits

  • Nothing was installed. A name that the lists promise but whose module fails to import in some environment would still raise; a name added by a package's own patching is not seen.
  • Only the first release of each minor version was read. A name that changed in a patch release is attributed to the next minor.
  • Submodule paths are not covered: from transformers.models.bert import ..., transformers.generation, transformers.modeling_utils and so on. A name that left the top level can still be importable from its submodule.
  • Releases before 2.0.0 (pytorch-transformers, pytorch-pretrained-bert) are not covered.
  • "Instead" is given only where the library's own deprecation message names a replacement, or for the whole groups described above. For other names the release notes of the release that dropped it are the place to look.

Questions

Why do I get "ImportError: cannot import name ... from 'transformers'"?

The installed transformers release does not export that name. Either the release is older than the one that added the name, or it is newer than the last one that had it. The name usually comes from your own code, a tutorial, or another package that was written for a different transformers release. Install a release inside the range that has the name, or change the import to its replacement.

Which transformers version removed AdamW?

transformers 4.50.0 (2025-03-21). AdamW is importable from transformers 2.0.0 through 4.49.0. The class's own deprecation warning names the replacement: torch.optim.AdamW.

Why did TFBertModel, TFAutoModel and the Flax classes disappear?

transformers 5.0.0 (2026-01-26) removed TensorFlow and Flax support. 428 names starting with TF and 212 starting with Flax stopped being exported in that release. They are importable through 4.57.6; with 5.x use the PyTorch class of the same model.

Does BertTokenizerFast still import in transformers 5?

Yes. From 5.0.0 the name is not in the import lists any more, but the lazy module resolves a name ending in TokenizerFast to the class without the suffix, so the import returns BertTokenizer. 47 tokenizer names and, from 5.4.0, 91 image processor names ending in ImageProcessorFast keep importing this way in 5.23.0.

Another package fails with this ImportError. What do I pin?

Pin transformers to the range that has the name: at least the first release that exports it and below the release that dropped it, for example pip install "transformers>=4.29.0,<4.52.1" for the agents classes. Then look for a newer release of the other package; a pin that old also holds back every model added since.
