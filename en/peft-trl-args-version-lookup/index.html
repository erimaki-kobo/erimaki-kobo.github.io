Answers for LLM inference engineers

"__init__() got an unexpected keyword argument": the PEFT, TRL or Transformers release each argument needs

"X.__init__() got an unexpected keyword argument 'y'" means the installed library does not have y on that class: it is older than the release that added it, or newer than the release that removed it. For a LoRA adapter the cause is almost always an older PEFT: use_rslora needs PEFT 0.8.0, use_dora 0.9.0, layer_replication 0.10.0, lora_bias 0.14.0. For training scripts it is usually a removed name: evaluation_strategy is gone after Transformers 4.50.3 (write eval_strategy), and TRL's SFTTrainer stopped taking dataset_text_field and max_seq_length after TRL 0.12.2. Paste the error or the adapter's config below.

Why does the same adapter raise TypeError on one machine and only a warning on another?

PEFT changed what it does with unknown keys in 0.14.0. Up to 0.13.2, loading a config with a key the installed PEFT does not know fails with TypeError: LoraConfig.__init__() got an unexpected keyword argument. From 0.14.0 the loader catches that error, removes the unknown keys and continues with a warning. PEFT 0.14.0 loading an adapter saved with 0.15.0 prints:

UserWarning: Unexpected keyword arguments ['corda_config', 'trainable_token_indices'] for class LoraConfig, these are ignored. This probably means that you're loading a configuration file that was saved using a higher version of the library and additional parameters have been introduced since. It is highly recommended to upgrade the PEFT version before continuing (e.g. by running `pip install -U peft`).

The warning is easy to miss, and the adapter then runs without the dropped settings. That is harmless when every dropped key held its default and wrong when one did not, for example a config saved with a newer variant switched on. Constructing a config in your own code, LoraConfig(use_dora=True), still raises TypeError on every release that lacks the argument; only loading from a file is lenient.

  • Fix that always works: upgrade PEFT to the release in the table, or newer.
  • Deleting the key by hand is the same as what 0.14.0 and later do automatically. PEFT's own troubleshooting page allows it only when the key is at its default value.
  • A key that was removed (enable_lora, merge_weights, last in 0.2.0) means the opposite direction: a very old adapter on a new PEFT.

How was this built?

  • Source: every final release tag of huggingface/peft (39), huggingface/trl (103) and huggingface/transformers from v4.0.0 (215), parsed with Python's ast. No library code was imported or run.
  • Config classes: the dataclass fields of the class plus those of its base classes in the same package (LoraConfig + PeftConfig + PeftConfigMixin; SFTConfig + TRL's base config). Fields declared init=False are left out.
  • Trainers: the parameters of __init__. A name handled by @deprecate_kwarg is counted as an alias for the releases that carry the decorator.
  • Replacements: taken from the deprecation message in the last release that still had the old name, and checked against the data: the build fails if a replacement did not exist in the stated release.
  • The 0.14.0 change: the first release whose src/peft/config.py catches the TypeError and warns (commit 85e3202a).

What this page does not cover

  • Nothing was executed. The page reports which names a constructor accepts, not whether a value is valid or what it does.
  • Changed defaults and changed behaviour of an argument that kept its name.
  • Transformers classes other than the four named above, and model or tokenizer from_pretrained arguments.
  • Release candidates, development installs and forks. An adapter saved from a PEFT source checkout can hold keys no release has yet.
  • Arguments passed through **kwargs to another library.

Questions

What does "LoraConfig.__init__() got an unexpected keyword argument" mean?
The adapter was saved with a newer PEFT than the one loading it: its adapter_config.json has a key your PEFT does not know. Each key has a first release, for example use_rslora 0.8.0, use_dora 0.9.0, layer_replication 0.10.0, lora_bias 0.14.0 and alora_invocation_tokens 0.18.0. Install at least the release of the newest key in the file. PEFT 0.14.0 and later no longer raise this error on load; they warn and ignore the unknown keys.
Is it safe to delete the unknown key from adapter_config.json?
Only if the key holds its default value, so that removing it changes nothing. A key such as use_dora set to true describes how the weights were trained; deleting it, or loading with PEFT 0.14.0 or later where it is ignored with a warning, loads a different model than the one that was saved. Upgrading PEFT is the safe fix.
Why does TrainingArguments reject evaluation_strategy?
evaluation_strategy was renamed to eval_strategy in Transformers 4.41.0. The old name kept working with a warning until 4.50.3 and is gone from 4.51.0. Write eval_strategy.
Why does SFTTrainer reject tokenizer, dataset_text_field or max_seq_length?
TRL moved them. tokenizer became processing_class in TRL 0.12.0; the old name was accepted with a warning until 0.15.2. dataset_text_field, max_seq_length and packing stopped being SFTTrainer arguments after 0.12.2 and belong on SFTConfig. On SFTConfig, max_seq_length was renamed to max_length in 0.16.0 and removed after 0.19.1.
Why does Trainer reject tokenizer?
Transformers 4.46.0 renamed the Trainer argument tokenizer to processing_class. The old name was accepted with a deprecation warning through 4.57.6 and removed in 5.0.0.
How do I find which PEFT version saved an adapter?
From PEFT 0.18.0 the file adapter_config.json records it in the key peft_version. Older files do not say; the newest key in the file gives a lower bound, which the lookup on this page computes.
