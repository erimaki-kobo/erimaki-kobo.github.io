Which MoE backend does vLLM use on RTX 50, RTX PRO 6000 and DGX Spark (SM120/SM121)?

Short answer for vLLM v0.34.0: on SM120 and SM121 the automatic choice is FLASHINFER_CUTLASS for NVFP4 MoE, TRITON for FP8 with block scales or dynamic activations, FLASHINFER_CUTLASS for FP8 with static per-tensor scales, and MARLIN for gpt-oss MXFP4. vLLM's own CUTLASS grouped FP8 kernel (VLLM_CUTLASS) is never usable on SM12x after v0.15.0: cutlass_group_gemm_supported() returns False for compute capability 11.0 and above. The error ... MoE backend 'X' does not support the deployment configuration appears only when a backend was forced; in auto mode vLLM skips that backend with a DEBUG log and tries the next one.

The one break is v0.15.0 to v0.15.1. In v0.15.0 the FlashInfer NVFP4 kernels only accepted SM90 and SM10x, so SM120 fell through to VLLM_CUTLASS, and anyone forcing FlashInfer got the error in #33416. The fix, PR #33417, first shipped in v0.15.1: it added is_device_capability_family(120) to flashinfer_cutlass_moe.py. The same release made cutlass_group_gemm_supported() return False for capability 11.0 and above, which moved FP8 per-channel models from VLLM_CUTLASS to TRITON.

What "does not support the deployment configuration" means

It means a backend was forced and that backend rejected this GPU or checkpoint. Each selector builds a priority list, asks every kernel class is_supported_config(), and returns the first that passes. When nothing is forced, a rejection is logged at DEBUG level only. When you set --moe-backend (v0.17.0 and later) or, before v0.24.0, VLLM_USE_FLASHINFER_MOE_FP4=1 together with VLLM_FLASHINFER_MOE_BACKEND, the same rejection is raised as a ValueError. To fix the error, remove the flag or variable and let auto pick, or choose a backend the tool marks yes for your GPU and release.

Selected is not the same as working

This page answers "which kernel will vLLM try". Whether that kernel then builds and produces correct output on SM12x is a separate question, and some public reports say it does not:

  • NVFP4 on SM120. A report from 4x RTX PRO 6000 describes grouped-GEMM initialization failures and garbage output from the native NVFP4 MoE kernels, with Marlin as the working path (forum report).
  • FP8 on SM12x falls to TRITON because CUTLASS has no SM120/SM121 grouped-GEMM builder for tensor- or token-scaled FP8 (#43507). That matches the code: vllm/_custom_ops.py returns False for capability 11.0 and above before calling the C++ check. The change proposed for it, PR #43814, is not in any release up to v0.34.0.
  • MARLIN MoE has a report of CUDA error: an illegal memory access under concurrent decode on RTX PRO 6000 with a W4A16 DeepSeek-V4-Flash checkpoint (PR #43730, which proposes a fix and is not in any release up to v0.34.0).
  • VLLM_MOE_FORCE_MARLIN, quoted in that forum report as the way to force Marlin, does not appear in the source tree of any vLLM release tag. Use --moe-backend marlin.

None of these were run on a GPU for this page.

How this was built

For each of the 29 releases from v0.15.0 to v0.34.0 (the releases that have the fused_moe/oracle/ selectors), the release's Python source was imported on a CPU machine with the compiled extensions stubbed out. current_platform was replaced by a CUDA platform that reports a chosen compute capability (8.0, 8.9, 9.0, 10.0, 10.3, 12.0, 12.1). Then the same selector the quantization method calls (select_nvfp4_moe_backend, select_fp8_moe_backend, select_mxfp4_moe_backend or, before v0.19.0, get_mxfp4_backend) was called with the weight and activation keys that method passes. The tool also asks every backend's kernel classes is_supported_config() and records the reason string vLLM itself produces. The scripts are in this site's repository.

Three things come from C++ in the real wheel and were re-implemented from the release's csrc/: cutlass_group_gemm_supported (SM90 needs CUDA 12.3, SM10x CUDA 12.8; the Python wrapper rejects capability below 9.0 or from 11.0 from v0.15.1), mxfp4_experts_quant_supported (10.0 to 11.9), and the dense FP8 checks, which do not affect MoE selection. All has_flashinfer_* checks were set to true (FlashInfer is a dependency of every release here). Check: setting the two environment variables from the forum thread on simulated SM120 in v0.15.0 reproduces the exact error text users posted.

Not covered: unquantized BF16 MoE, INT4/INT8 MoE (AWQ, GPTQ, W4A16, W8A8-int), expert or tensor parallel (which change the activation format and the list), LoRA, VLLM_BATCH_INVARIANT, ROCm. Selection can still change at run time for unusual shapes ("Shape-specific fallbacks may still occur at runtime", in the selector's docstring). Nothing here was run on a GPU.

FAQ

What does "MoE backend ... does not support the deployment configuration" mean in vLLM?

A backend was forced with --moe-backend (or, before v0.24.0, with VLLM_USE_FLASHINFER_MOE_FP4 / VLLM_FLASHINFER_MOE_BACKEND) and that backend rejected this GPU or checkpoint. In auto mode the same rejection is only a DEBUG log and vLLM tries the next backend. Remove the flag or variable, or force a backend that passes the checks, such as marlin.

Should I force --moe-backend marlin on an RTX 5090 for NVFP4?

If the default FLASHINFER_CUTLASS fails to start or produces garbage, the public report above used Marlin as the working path. Marlin runs NVFP4 weights with 16-bit activations, so it is a weight-only path. It passes vLLM's checks on SM120 in every release from v0.15.0.

Why does VLLM_NVFP4_GEMM_BACKEND do nothing for my MoE model?

It chose the kernel for dense (linear) NVFP4 layers, not MoE layers. It existed from v0.11.1 to v0.23.0, was deprecated in v0.22.0 with the message "Use --linear-backend.", and is not in vllm/envs.py from v0.24.0. MoE layers follow --moe-backend.

Is DGX Spark (SM121) different from RTX 50 (SM120)?

Not for MoE selection: in every release and format here the automatic pick is the same for 12.0 and 12.1, because the checks use is_device_capability_family(120).
