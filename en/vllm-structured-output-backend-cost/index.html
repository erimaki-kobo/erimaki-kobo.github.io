vLLM structured output: which backend runs your JSON schema, and why it is slow

vLLM picks one structured output backend when the server starts, and a request cannot change it. With the default, auto, each JSON schema goes to xgrammar unless vLLM finds a keyword xgrammar is known to mishandle; then it silently goes to guidance (llguidance), or to outlines for patternProperties. So two schemas on the same server can run on different engines with different speed. Most “guided decoding is slow” reports come down to one of four causes: compiling a new schema, landing on the fallback backend, the model padding the JSON with whitespace until max_tokens, or a request that is not constrained at all because it still sends guided_json, which vLLM removed in v0.12.0. The checker below tells you which backend your schema gets; the script measures the other three on your own server.

Which backend will vLLM use for my schema?

Paste a JSON schema, or a whole request body (response_format, structured_outputs or the old guided_json are all read).

Runs in your browser; nothing is sent anywhere. Your vLLM version: vllm --version or pip show vllm. This applies to --structured-outputs-config.backend auto, the default. If you set a backend explicitly, that backend is used for every request, and with xgrammar a schema that fails the check gets HTTP 400.

Which JSON Schema keywords send a schema off xgrammar?

In auto mode, vLLM runs a pre-check on every schema before handing it to xgrammar. If any node in the schema matches a row marked “falls back” for your version, the request goes to guidance (or outlines, see the next table). The check walks the whole schema, including $defs, anyOf branches and array items, so one keyword deep inside is enough.

Where does auto go when xgrammar is rejected?

Usually to guidance. It goes to outlines instead when the schema contains patternProperties or the model uses an older, non-Tekken Mistral tokenizer, and from v0.32.0 the request fails with HTTP 400 if guidance cannot use the tokenizer.

v0.8.4 – v0.11.xUses guidance. (auto became the default for the V1 engine in v0.8.4; before that the default was xgrammar.)
v0.12.0 – v0.13.xUses outlines if the model uses a Mistral tokenizer; otherwise guidance.
v0.14.0 – v0.19.xUses outlines if the tokenizer is a Mistral tokenizer or the schema contains patternProperties anywhere; otherwise guidance.
v0.20.0 – v0.30.xSame, but only non-Tekken Mistral tokenizers go to outlines; Tekken ones use guidance.

The server log does not say which backend a request ended up on. The checker above repeats vLLM's decision for JSON schemas.

Which request fields work in which vLLM version?

Send the schema in response_format with "type": "json_schema"; that works in every version. The old guided_json field stopped working in v0.12.0 and is ignored without an error.

response_format with "type": "json_schema" works in every version on this page and on other OpenAI-compatible servers, so it is the safest way to send a schema. Use structured_outputs when you need a vLLM-only option such as disable_any_whitespace.

How do I measure what structured output costs on my server?

sotime.py sends the same prompt four ways and compares time to first token, time per token, output length and whether the output matches the schema. It needs only Python 3.8+ and works with any OpenAI-compatible endpoint (vLLM, SGLang, llama.cpp server).

curl -O https://erimaki-kobo.github.io/en/vllm-structured-output-backend-cost/sotime.py
python sotime.py --base-url http://localhost:8000/v1 --model Qwen/Qwen3-8B --no-think
python sotime.py --base-url http://localhost:8000/v1 --model Qwen/Qwen3-8B --schema my_schema.json -n 10
free
No constraint. The baseline for speed and length; it also shows how often the model already follows the schema on its own.
warm
The same schema every time via response_format. The first request is reported separately because it pays grammar compilation; the rest show the cached cost.
cold
A schema that differs on every request (a random description), so no grammar cache helps. This is your cost if every request brings its own schema, as with tool calling or per-user forms.
compact
vLLM only: the same schema with disable_any_whitespace. Compare it with warm to see whether whitespace is costing you tokens.

Built-in schemas: flat (a small record), nested (an invoice with an array of objects, an enum and a pattern) and fallback, which uses uniqueItems and pattern with maxLength, so on a default vLLM server it runs on guidance. Run --builtin all to see the xgrammar and guidance paths side by side on one server.

To compare backends directly, start vLLM twice and label the runs:

vllm serve Qwen/Qwen3-8B --structured-outputs-config.backend xgrammar
python sotime.py --base-url http://localhost:8000/v1 --model Qwen/Qwen3-8B --label xgrammar --json xg.json
vllm serve Qwen/Qwen3-8B --structured-outputs-config.backend guidance
python sotime.py --base-url http://localhost:8000/v1 --model Qwen/Qwen3-8B --label guidance --json gd.json

Exit codes: 0 constrained output looked fine; 1 the constraint was not applied or outputs broke the schema; 3 runaway whitespace; 2 could not run. Requests go one at a time by default so that TTFT shows compilation rather than queueing; add --concurrency to measure under load.

FAQ

Can I choose xgrammar or guidance per request in vLLM?
No. The backend is set once when the server starts, with --structured-outputs-config.backend (default auto). A request that names a different backend is rejected. To compare backends, start the server once per backend and run the same requests against each.
Why is guided decoding slow in vLLM?
Usually one of four things: the first request with a new schema pays grammar compilation; the schema uses a keyword that sends auto mode from xgrammar to guidance or outlines; the model emits whitespace between JSON tokens until max_tokens; or the constraint is not applied at all because the request still uses guided_json, which vLLM removed in v0.12.0. The script on this page reports which of these you have.
Does vLLM still accept guided_json?
Not since v0.12.0. guided_json, guided_regex, guided_choice, guided_grammar, guided_decoding_backend and guided_whitespace_pattern were deprecated in v0.11.0 and removed in v0.12.0. The server ignores them and returns unconstrained text. Use response_format with type json_schema, or structured_outputs with json.
Which JSON Schema keywords make vLLM fall back from xgrammar?
In vLLM v0.32.0 and later: multipleOf on numbers; uniqueItems, contains, minContains or maxContains on arrays; a string format outside xgrammar's 14 formats; pattern or format together with minLength or maxLength; propertyNames together with properties or patternProperties; patternProperties together with properties or with two or more patterns; and allOf with two or more branches. The table on this page gives each version.
How do I stop the model from generating endless whitespace in JSON mode?
Set disable_any_whitespace. In vLLM it can be set per request inside structured_outputs, or for the whole server with --structured-outputs-config.disable_any_whitespace true. It works with the xgrammar and guidance backends.
Is lm-format-enforcer still supported in vLLM?
It still works in v0.33.0 but logs a deprecation warning; vLLM says it will be removed in v0.35.0. Use auto, xgrammar or guidance instead.

Limitations

  • The checker repeats vLLM's pre-check and fallback rules for JSON schemas. It does not run xgrammar's own compiler, so a schema the pre-check passes but xgrammar cannot compile will show xgrammar here and fall back on the server.
  • Regex, choice, grammar and structural-tag requests are not checked; the fallback table still applies to them.
  • No speed numbers are given on this page. Which backend is faster depends on the schema, the model's tokenizer and the load, and published comparisons disagree; sotime.py measures it on your setup. The script was tested against a mock server, not a GPU.
  • Release dates are the dates of the tag commits.
