ImportError: cannot import name 'X' from 'diffusers' (or diffusers.utils, diffusers.models ...): which releases have it

The error has one of three causes: your diffusers is older than the release that added the name, the name was removed, or it moved to another module. Added: FluxPipeline needs diffusers 0.30.0, WanPipeline 0.33.0, StableDiffusion3Pipeline 0.29.0. Removed: the ONNX pipelines in 0.43.0 (2026-11-12; last release with them 0.42.1), the Flax classes in 0.40.0 (2026-08-20; last 0.39.0), the k-diffusion pipelines in 0.37.0 (2026-03-05; last 0.36.0). Moved: randn_tensor left diffusers.utils in 0.21.0 (2023-09-13) and imports from diffusers.utils.torch_utils in every release since 0.12.0. For any other name, in any module of diffusers, paste the error below.

How do I read the error?

  • The module after "from" matters as much as the name. from 'diffusers' is the top level; from 'diffusers.utils' or a longer path is a module whose contents change more often. Paste the whole line so the lookup uses the right module.
  • The path in parentheses is the copy of diffusers that was imported. Check that it is the version you expect: python -c "import diffusers as d; print(d.__version__, d.__file__)". In a notebook, restart the kernel after upgrading.
  • "Failed to import diffusers.pipelines... because of the following error" wraps a second error. If that one names transformers or huggingface_hub (cannot import name 'cached_download' from 'huggingface_hub' is the common one), diffusers is fine and the other package is too new or too old: see the pages linked at the bottom.
  • No error on import, then "requires the torch library" (or transformers, onnxruntime, ...) when the class is used: the name exists, and diffusers gave you a placeholder because that backend is not installed. Install the backend; the diffusers version is not the problem.
  • "Did you mean: ...?" at the end is Python's spelling suggestion, not advice from diffusers.

How was this read, and how was it checked?

From the source of each release tag, with Python's ast module; no release was installed or imported.

  • Up to 0.20.x, diffusers/__init__.py imports its names eagerly, and the names are the ones those import statements bind. From 0.21.0 (2023-09-13) the top level and most packages below it replace themselves with a lazy module that serves the names of one table (_import_structure). The table is read along the path taken when the optional backends are installed; each entry is then followed to the file it names, down to the definition.
  • For any other module, the names are everything it binds at module level: classes, functions, assignments and imports. Code under if TYPE_CHECKING: is skipped, because it does not run.
  • The lazy module's own lookup code (_LazyModule.__getattr__) is checked in every release for rules that look at the spelling of a name; it has none, and the build stops if one appears.
  • Dates and yanked releases come from PyPI.

Checks, all by a second reading: (1) every lazy package repeats its names as plain imports for type checkers; in 1713 of 2008 package-and-release pairs that block and our reading are identical, and the other pairs differ by 49 names that upstream lists in only one of the two places (the lookup follows the table, which is what runs). (2) Each of the 798 top-level names is found as plain text in __init__.py of every release in its range (12039 name-and-release pairs), and is absent from the release on either side of the range (803 edges). (3) A regular expression finds 60015 class, function and variable definitions in 7595 file versions; all are among the names read. (4) The placeholders the top level hands out when a backend is missing are the same names as the real ones, except for the stale entry above. (5) 23 known facts hold, among them the releases named in the public error reports under Sources.

Limits

  • Nothing was installed or run. "Has it" means the import statement resolves in the source; it does not mean the class works with your versions of torch or transformers.
  • Only the first release of each minor version was read. A change made in a patch release is attributed to the next minor.
  • The answer assumes the optional backends are installed. Without one, a top-level import of a name that needs it still succeeds and returns a placeholder; a few packages below the top level then hand out more placeholders than they have real names.
  • Importing a name can still fail for another reason: the file that defines it imports something your transformers or huggingface_hub does not have. That shows up as "Failed to import ..." with a second error underneath.
  • "Instead" is given only where the source of the last release with the name states it, or where the same name is defined elsewhere in 0.43.0. Community pipelines (custom_pipeline=...) and forks are not covered.

Questions

Which diffusers version has FluxPipeline?

diffusers 0.30.0 (2024-08-07) and every release after it. On an older release, or on a 0.30.0.dev0 build made before the pipeline was merged, "from diffusers import FluxPipeline" fails with ImportError. Upgrade: pip install -U "diffusers>=0.30.0".

How do I fix "cannot import name 'randn_tensor' from 'diffusers.utils'"?

Change the import to "from diffusers.utils.torch_utils import randn_tensor". diffusers.utils exported randn_tensor from 0.12.0 through 0.20.2 and stopped in 0.21.0 (2023-09-13); diffusers.utils.torch_utils has had it since 0.12.0, so the new import works on old and new releases. If the import is inside a package you do not maintain, pin instead: pip install "diffusers<0.21.0".

Why can't I import OnnxStableDiffusionPipeline from diffusers any more?

diffusers 0.43.0 (2026-11-12) removed the ONNX Runtime pipelines and OnnxRuntimeModel; 0.42.1 is the last release that has them. The deprecation message in 0.42.1 says: "Please use Optimum for ONNX Runtime support." To keep the old code running: pip install "diffusers<0.43.0".

Which diffusers version removed the Flax classes?

diffusers 0.40.0 (2026-08-20) removed all 20 Flax names from the top level, FlaxStableDiffusionPipeline and FlaxUNet2DConditionModel included; 0.39.0 is the last release that has them. Its message recommends migrating to the PyTorch classes or pinning the version.

My diffusers is newer than the version the name needs, and the import still fails. Why?

Three usual reasons. Another copy of diffusers is being imported: print diffusers.__version__ and diffusers.__file__ in the same interpreter. The install is a development build (for example 0.30.0.dev0) made before the name was merged. Or the error names another package: "Failed to import diffusers.pipelines... because of the following error: cannot import name ... from 'transformers'" is about transformers or huggingface_hub, not diffusers.

The name in my error is not a pipeline. Does this page cover it?

Yes. The lookup covers every name that every module of diffusers binds, from 0.0.2 to 0.43.0: 798 top-level names (51 gone from the newest release) and 37577 module-and-name pairs across 1380 modules, 228 of which no longer exist.
