"unknown model architecture": which llama.cpp build and Ollama version a GGUF needs

"unknown model architecture: 'X'" means the llama.cpp inside your runtime is older than the commit that added X. The fix is a build at or above the number in the table below. For example, gemma4 needs llama.cpp b8637 (2026-04-02) and qwen35, used by Qwen 3.5 and 3.6, needs b7990 (2026-02-10). Ollama's bundled llama.cpp has both from 0.30.0. llama.cpp b12316 knows 172 architecture strings, 60 of them added in 2026. The latest Ollama, 0.40.16, bundles b12177, so it cannot yet load kimi-k31 (b12180).

Which build does my GGUF need?

Paste the error line, or type the value of general.architecture. The two version fields are optional; fill them in to get a yes or no for your install.

Runs in your browser on the table below; nothing is sent anywhere. Build number: llama-server --version. Ollama version: ollama --version. Architecture of a file: gguf-dump --no-tensors model.gguf (pip install gguf).

Why did Ollama say "unknown model architecture" for a model it listed as supported?

Between 0.5.12 and 0.31.1 Ollama had two loaders, and a file that its own engine could not take fell back to the older bundled llama.cpp. In that period 9 architectures were registered in Ollama's own engine before the bundled llama.cpp knew them. gemma4 is the clearest case: the own engine has it from 0.20.0, while the bundled llama.cpp stayed at b7437 until 0.30.0.

The loader at the v0.24.0 tag tries the own engine for a fixed list of architectures, refuses models that come with a separate projector file ("split vision models aren't supported"), and on any failure switches to the bundled llama.cpp. So a model pulled from the Ollama library worked, while a Hugging Face GGUF with a separate mmproj file, or with a layout the own engine did not expect, reported "unknown model architecture" from the old llama.cpp. From 0.31.2 the own-engine model code is gone and the bundled llama.cpp column is the whole answer.

Ollama's own engine also used its own names in places: it registered gptoss first and added the upstream spelling gpt-oss later. The column above only counts exact matches with the upstream string.

The build is new enough and the model still fails. What else is there?

  • The app did not actually update its runtime. Desktop apps ship llama.cpp as a separate runtime package that can stay on an old version after the app updates. Check the runtime version the app reports, not the app version.
  • The file was re-uploaded for a newer build. Converters change, and uploaders replace files. A GGUF published today can need tensors or metadata that the first supporting build did not read. Use the newest build before debugging anything else.
  • Extra blocks in the file. GGUFs that embed multi-token-prediction (nextn) layers or a vision projector need support for that feature in addition to the base architecture.
  • A fork-only architecture. If the lookup says the name is not in upstream llama.cpp, the file targets a fork or a pull request that is not merged. The model card usually names it.
  • The file is incomplete. A truncated download fails earlier, with a magic-number or tensor-data error instead of an architecture error.

Does vLLM read the same architecture strings?

No. vLLM does not use llama.cpp; it maps GGUF tensors onto its own PyTorch model classes, so a GGUF that llama.cpp loads can still fail in vLLM. GGUF loading moved out of vLLM into vllm-gguf-plugin in v0.24.0 (2026-06-27). The plugin's README lists the families covered by its generation tests: Qwen 2.5, Qwen 3, Phi 3.5, GPT-2, StableLM, Gemma 3, OLMoE, Gemma 4, Qwen 3.5 and Qwen 3.6. It states that other vLLM-supported architectures may work when their tensor names map to the Hugging Face model, and that being a vLLM-supported model does not guarantee GGUF compatibility.

uv pip install vllm-gguf-plugin
vllm serve unsloth/Qwen3-0.6B-GGUF:Q4_K_M --tokenizer Qwen/Qwen3-0.6B

On vLLM older than v0.24.0 the built-in loader relied on the Transformers GGUF parser, and the message was "GGUF model with architecture ... is not supported yet".

How was this table built?

  • Architecture strings: every { LLM_ARCH_*, "name" } entry at llama.cpp b12316 (2026-11-12).
  • Introducing commit: the oldest commit whose diff adds the entry, following the table through the January 2025 file split back to its first appearance in August 2023.
  • First build: git describe --contains --match "b*" on that commit.
  • Ollama pin: at each of 273 release tags, LLAMA_CPP_VERSION, or FETCH_HEAD in Makefile.sync, or LLAMACPP_BASE_COMMIT in llama/vendoring, or the llm/llama.cpp submodule commit, resolved against the llama.cpp history. 234 tags resolve.
  • Ollama patches: the architecture table in the vendored, already patched source at 0.3.13 to 0.24.0, and added LLM_ARCH entries in the patch directories of the other releases. This moves 5 rows earlier than the pin alone would.
  • Own engine: model.Register("...") calls under model/models at each tag.
  • vLLM: the plugin README at v0.0.5 and the vLLM commit that moved GGUF out of the main repository.

What this page does not cover

  • No model was loaded for this page. It reports when a name entered the source, which is the condition for the "unknown model architecture" error and nothing more.
  • Ollama carries patches on top of its pinned llama.cpp. For releases that keep the patched source in the repository (0.3.13 to 0.24.0) the table reads that source, and for the others it reads the architecture entries in Ollama's patch files; rows marked "Ollama patch" come from there. Other effects of those patches were not examined.
  • LM Studio, Jan, KoboldCpp, llama-cpp-python and other bundlers are not mapped. Each bundles some llama.cpp build; once you know that build number, the first table applies.
  • Architectures removed from llama.cpp before b12316, and names that exist only in forks, are not listed.
  • Regenerated when new architectures land; the "as of" date at the top says how current it is.

Questions

What does "unknown model architecture" mean when loading a GGUF?
The file's general.architecture value is a name the llama.cpp build inside your runtime does not have in its architecture table. The file is usually fine. The runtime is older than the commit that added that architecture; the table above gives the first build that has it.
Which llama.cpp build do I need for Gemma 4 GGUF files?
gemma4 first appears in build b8637 (2026-04-02). Ollama's bundled llama.cpp has it from 0.30.0; Ollama's own engine registered gemma4 from 0.20.0 to 0.31.1.
Which llama.cpp build do I need for Qwen 3.5 and Qwen 3.6 GGUF files?
Both families use the architecture string qwen35 (MoE variants use qwen35moe). qwen35 first appears in build b7990 (2026-02-10), and Ollama's bundled llama.cpp has it from 0.30.0.
How do I find which llama.cpp version my Ollama uses?
From Ollama 0.30.0 the repository has a LLAMA_CPP_VERSION file at each release tag holding the llama.cpp tag, for example b12177 for Ollama 0.40.16. Older releases pin a commit in Makefile.sync, llama/vendoring or a git submodule; the second table on this page resolves all of them to build numbers.
How do I read the architecture string of a GGUF file?
Run gguf-dump --no-tensors model.gguf from the gguf Python package and read general.architecture. llama.cpp also prints it while loading, and the Hugging Face file viewer shows it in the metadata panel of a .gguf file.
My build is new enough and the model still fails to load. Why?
A known architecture name is necessary, not sufficient. Later commits add tensors, metadata keys, tokenizer types or multimodal projectors for the same architecture, and re-uploaded GGUF files can depend on them. Use the newest build first; if it still fails, the cause is in the file or a missing feature, not the architecture table.
Can vLLM load any GGUF architecture?
No. From vLLM v0.24.0 GGUF loading lives in the separate vllm-gguf-plugin, which maps GGUF tensors onto vLLM's own model classes. Its README lists the families covered by tests (9 architecture strings in the table above) and says other models may or may not work.
