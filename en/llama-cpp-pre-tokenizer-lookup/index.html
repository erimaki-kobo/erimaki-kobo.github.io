"BPE pre-tokenizer was not recognized" and "unknown pre-tokenizer type": which llama.cpp build fixes it

Both errors usually mean your llama.cpp is older than the commit that added your tokenizer. When converting, look up the chkhsh printed above the error; when loading, look up the tokenizer.ggml.pre name in the error. Use a build at or above the one in the table. For example, the chkhsh 1444df51289c... that a fine-tuned Qwen3.5-4B printed is recognized from b9049 (2026-05-06), and a GGUF with qwen35 loads from b7990 (2026-02-10), Ollama 0.30.0 and llama-cpp-python 0.3.17. llama.cpp b12754 knows 104 hashes and 101 names; 34 of the names were added in 2026.

My chkhsh is not in the table. What now?

Then no llama.cpp version recognizes your tokenizer yet, and upgrading does not help. The hash changes whenever the token ids for the test string change. Common causes:

  • You changed the tokenizer while fine-tuning: added tokens, a different normalizer or pre-tokenizer, or a tokenizer.json re-saved by another transformers version. If you did not mean to, copy the base model's tokenizer.json, tokenizer_config.json and special_tokens_map.json into the folder and convert again.
  • The model family is new and llama.cpp has no entry yet. Wait for the model support PR, or add the model to convert_hf_to_gguf_update.py and regenerate, which is what that PR does.
  • Your tokenizer is a known one with a small difference. If you are sure the split rules are the same as a listed model's, you can add your hash to your local copy of get_vocab_base_pre() with that model's name. A wrong choice gives a file that loads and tokenizes slightly differently from Transformers, so compare token ids on a few strings afterwards.

The tool above answers in the same way: a hash that is not listed gets "not recognized by any build up to b12754".

Can I rename the pre-tokenizer instead of upgrading?

Sometimes. The current loader treats some names identically, so a file tagged with a new name can be re-tagged with an older name that your runtime already knows. For example, glm5 (b11279) has the same handling as glm4 (b5115):

pip install gguf
gguf-new-metadata --pre-tokenizer glm4 model.gguf model-glm4pre.gguf

Three conditions: the target name must be in the "same handling as" column; your build must know the target name; and your build must also know the model architecture, which is often the real blocker (see the architecture lookup). "Same handling" is read from the current source; an older build may have had different rules for the same name. Compare the token ids with Transformers on a few strings after re-tagging.

Two names for one hash: the last entry wins

A few tokenizers give the same chkhsh as another model. get_vocab_base_pre() is a list of plain if statements, so the last matching entry decides the name. At b12754:

  • 0876d13b5074...: bert-bge (BAAI/bge-small-en-v1.5), then jina-v2-en (jinaai/jina-embeddings-v2-base-en); the converter writes jina-v2-en
  • b6dc8df998e1...: mpt (mosaicml/mpt-7b), then olmo (allenai/OLMo-1.7-7B-hf); the converter writes olmo
  • 32d85c31273f...: stablelm2 (stabilityai/stablelm-2-zephyr-1_6b), then domyn-edge (domyn/Domyn-Edge-Teacher-IF); the converter writes domyn-edge

The newest case matters for StableLM 2: since b12568 (2026-11-20), converting a StableLM 2 checkpoint writes domyn-edge instead of stablelm2. Runtimes older than b12568 then refuse the file with unknown pre-tokenizer type: 'domyn-edge'; Ollama has the name from 0.40.18 and llama-cpp-python from 0.3.38. The split rules are the same, but domyn-edge is handled like qwen2 (spaces are not cleaned up when decoding), not like stablelm2. To keep the old behaviour: gguf-new-metadata --pre-tokenizer stablelm2 in.gguf out.gguf. This is read from the source; we did not convert a StableLM 2 model.

How was this built?

From the llama.cpp repository: every first-parent commit since 2024-04 that touched the converter (convert-hf-to-gguf.py, convert_hf_to_gguf.py, conversion/base.py) or the loader's name list (llama.cpp, src/llama.cpp, src/llama-model.cpp, src/llama-vocab.cpp), 1175 commits. For each commit we parsed the full list of hashes (including if chkhsh == A or chkhsh == B) and names, so a hash that was added, removed and added again is dated from its last addition. The first release is the first bNNNN tag that contains the commit (git describe --contains). As a check, the lists implied by the history were compared with the source of 55 sampled release tags; all matched. Ollama and llama-cpp-python: the llama.cpp commit each release pins, tested with git merge-base --is-ancestor against the commit that added the name. Download: pretok.json.

  • Models whose GGUF vocabulary is not BPE.

  • Commits after b12754: raon is on master but in no release yet.

Questions

What does "BPE pre-tokenizer was not recognized - update get_vocab_base_pre()" mean?
The converter encodes a fixed test string with your tokenizer, hashes the token ids (the chkhsh) and looks the hash up in a list. Your hash is not in the list of the convert_hf_to_gguf.py you ran. If the hash is in the table on this page, a newer llama.cpp checkout knows it; if it is not, your tokenizer differs from every tokenizer llama.cpp has registered.
What does "unknown pre-tokenizer type" mean when loading a GGUF?
The file's tokenizer.ggml.pre value is a name your llama.cpp build does not accept. Use a build at or above the one listed for that name, or the Ollama or llama-cpp-python release listed next to it.
I fine-tuned a model and now the chkhsh is unknown. Why?
The hash covers the whole tokenizer behaviour, so added tokens, a changed normalizer or pre-tokenizer, or a tokenizer.json saved by a different transformers version can change it. Convert with the base model's tokenizer files if you did not mean to change the tokenizer.
Can I rename tokenizer.ggml.pre instead of upgrading?
Only to a name that the current loader handles identically, listed in the "same handling as" column, and only if your build knows that name. gguf_new_metadata.py --pre-tokenizer writes a copy of the file with the new value. Check the tokenization afterwards.
What does "missing pre-tokenizer type, using: 'default'" mean?
The GGUF has a BPE vocabulary but no tokenizer.ggml.pre, usually because it was converted before b2761 (PR #6920). llama.cpp falls back to a generic split and warns that quality will be degraded. Re-convert or download a newer conversion.
