Two llama.cpp columns. "String from" is the first build whose loader knows the GGUF architecture string; "Converter knows the class from" is the first build whose convert_hf_to_gguf.py registers the Hugging Face class. When the second is later, the model reuses an older string (Qwen2.5-VL, DeepSeek-V3 / R1, Kimi K2.5): a GGUF of that model is written by the newer converter, so use a build at least that new. Classes the converter already had by b2700 (April 2024) show a dash there, because before that the converter was being restructured and the first appearance of a class does not mean new support.

The order is not always Transformers first. Kimi K2.5 ran in vLLM from v0.15.0, months before Transformers registered kimi_k25 in v5.13.0; until then it loaded in Transformers only with trust_remote_code=True. DeepSeek-V2 waited even longer: vLLM v0.5.1, Transformers v4.54.0. Mistral Large 4 is in Transformers v5.22.0 but has no native vLLM class up to v0.33.0.

Is the first release that registers a model enough?

The table gives the first release that knows the name. It is the floor, not a promise that everything works there. Support for a new model is often fixed in the next one or two patch releases, and other projects then raise their own minimum: Qwen3.5 was registered in Transformers 5.2.0, while the lmms-engine migration guide asks for Transformers 5.3.0 for it. For a model released in the last few months, install the newest patch release of the line, not the first one.

  • trust_remote_code models: if config.json has an auto_map, Transformers can run the model's own code with trust_remote_code=True, often before native support. That code has its own requirements, written on the model card. This page covers native support only.
  • Removed model types: 28 model types left Transformers after their last release, mostly old research models dropped in v5. The full table marks them.
  • Other dependencies: a new model can also need a newer tokenizers, torch, or for vLLM a newer kernel package. The error then names that package, not the architecture.

What happens in vLLM when the architecture is missing?

From v0.7.2 vLLM falls back to the Transformers implementation when none of the names in architectures is registered and the Transformers class is compatible. With the default --model-impl auto this is silent; --model-impl transformers forces it and reports why it cannot. The installed Transformers must then know the model too, so both versions in the lookup matter.

  • 23 names that vLLM once implemented itself now run through that backend on purpose (for example Olmo2ForCausalLM, native up to v0.25.1).
  • 50 names were removed and raise "was supported in vLLM until vY" (for example QWenLMHeadModel, the first Qwen, until v0.23.0).
  • 5 names moved to plugins, such as BART to bart-plugin.
  • Pooling variants (...ForSequenceClassification, ...Model) that are not registered are converted from the generative class of the same model in v0.33.0; the lookup shows the base class.

GGUF files in vLLM go through a separate plugin; see the GGUF page.

How is the GGUF architecture found from config.json?

llama.cpp's converter (convert_hf_to_gguf.py) registers each Hugging Face architecture name with a GGUF architecture, and that string is what llama.cpp checks when it loads the file. The names often differ: MistralForCausalLM becomes llama, DeepseekV3ForCausalLM becomes deepseek2, Qwen3_5ForConditionalGeneration becomes qwen35. The lookup uses the converter at llama.cpp b12352 (312 names), the first build whose converter registers each class (binary search over the release tags), and the build numbers of the strings from the GGUF lookup, which is regenerated daily.

How was this built?

  • Transformers: at each of 214 final release tags from v4.0.0 to v5.22.2, every ("model_type", "...Config") pair in models/auto/configuration_auto.py, and in auto_mappings.py where newer releases moved the table. "First release" is the first tag that contains the name; release candidates are not counted.
  • vLLM: at each of 98 final release tags from v0.1.0 to v0.33.0, the model registry (model_loader.py, then models/__init__.py, then models/registry.py). Native classes only; the Transformers-backend, removed and plugin lists of v0.33.0 give the status column.
  • Architecture to model_type: the MODEL_FOR_*_MAPPING_NAMES tables in modeling_auto.py at v5.22.2.
  • GGUF: @ModelBase.register(...) and model_arch in llama.cpp's conversion/ package at b12352, text models only. The first build registering each class: binary search over the bNNNN tags in convert_hf_to_gguf.py (and convert-hf-to-gguf.py, and conversion/ after the split). Results before b2700 are dropped: the register decorator itself appeared in b2318 and Llama and Mistral moved into it in b2573.

What this page does not cover

  • No model was loaded. The tables say when a name entered each library, which is what these errors check, and nothing about speed or correctness.
  • SGLang, TGI, MLX and TensorRT-LLM are not mapped. For llama.cpp-based runtimes other than Ollama, use the build number with the GGUF lookup.
  • Code on the main branch that is not yet in a release is not counted. If the lookup says "not in any release", the model may already be on main.
  • Regenerated when new releases of Transformers or vLLM appear; the "as of" date at the top says how current it is.

Questions

What does "KeyError" or "does not recognize this architecture" mean in Transformers?
The model_type in config.json is not in the AutoConfig table of your installed Transformers. Before v4.37.0 the error is a bare KeyError with the name, for example KeyError: 'qwen2'; from v4.37.0 it reads "The checkpoint you are trying to load has model type X but Transformers does not recognize this architecture". Install the release from the table on this page or newer.
Which Transformers version do I need for Qwen3?
Transformers 4.51.0 (released 2025-04-05) is the first release with model_type qwen3. vLLM has Qwen3ForCausalLM natively from 0.8.4, and llama.cpp reads Qwen3 GGUF files from build b5092.
Which versions do I need for Qwen3.5 or Qwen3.6?
Both use model_type qwen3_5 (qwen3_5_moe for the MoE models). Transformers 5.2.0 is the first release with it, vLLM 0.17.0 the first with a native class, and the GGUF architecture is qwen35 from llama.cpp b7990. Use the newest patch release, because fixes for new models often land after the first support.
Which versions do I need for Gemma 4?
Transformers 5.5.0, vLLM 0.19.0 and llama.cpp b8637 are the first releases that know Gemma 4 (model_type gemma4, architecture Gemma4ForConditionalGeneration).
What does "Model architectures ['X'] are not supported for now" mean in vLLM?
None of the names in the architectures list of config.json is in your vLLM's model registry, and the Transformers fallback did not apply. Upgrade to the release in the table, or, for a model vLLM never implemented, run it through the Transformers modeling backend with --model-impl transformers (vLLM 0.7.2 and later).
My versions are new enough and the model still fails. Why?
Being registered is the minimum, not a guarantee. New models often need a fix in the next patch release, a newer tokenizer or a newer kernel library. Install the newest patch release first. If config.json has an auto_map and you pass trust_remote_code=True, the repository's own code runs, and its requirements come from the model card.
