llama-server “forcing full prompt re-processing due to lack of cache data”: why the whole prompt is processed again, and how to find the cause

The message means the new prompt is not a pure continuation of the cached one, and the model's memory cannot be rolled back to the first changed token. A full-attention model (Llama, dense Qwen3) then re-processes only the tokens after the change. A sliding-window (SWA) model such as Gemma keeps only the last window of KV, and a hybrid or recurrent model (Qwen3.5, Qwen3-Next, Nemotron-H, Granite hybrid, LFM2, Mamba, RWKV) keeps one state at the end. Without a context checkpoint before the change, llama-server starts again from token 0. In our tests the same early edit cost 960 tokens on a full-attention model and the whole 1,821 to 1,852-token prompt on SWA and recurrent models. So the first question is not which flag to set but where the prompt changed. cachecheck.py answers that from two requests or from the server's own prompt log.

How do I find out why llama-server reprocesses the whole prompt?

Check three numbers: where two consecutive prompts stop sharing tokens, how many tokens the server reused (timings.cache_n), and what kind of memory the model has.

  1. Find the first changed token. Start the server with --log-prompts-dir DIR (build b9577 and later; it writes every rendered prompt as a .txt), make two turns in your client, then: 
    python cachecheck.py diff DIR/<first>.txt DIR/<second>.txt --server http://127.0.0.1:8080
    It prints the shared prefix in tokens and the text around the first difference, e.g. 
    turn 1: 1647 tokens   turn 2: 1821 tokens   shared prefix: 898 tokens
PREFIX CHANGED at token 898 of 1647 (55% into turn 1).
  turn 1: ... united in  ┃ while firs
  turn 2: ... united in  ┃ error first
    With saved request bodies instead (/v1/chat/completions JSON) it renders them through the server's own /apply-template, so the chat template, tools and reasoning handling are exactly the server's.
  2. Compare with what the server reused. Every llama-server response carries timings.cache_n (tokens taken from the cache) and timings.prompt_n (tokens processed). cachecheck.py live turn1.json turn2.json sends both requests and prints a verdict (below). If the shared prefix equals turn 1 and cache_n is still 0, the problem is on the server side.
  3. Know the model's memory. python cachecheck.py gguf model.gguf reads the GGUF header: full attention, SWA (with the window size), recurrent or hybrid. The server's startup log says the same in print_info: n_swa = ....

To read the server's own reasoning, restart it with -lv 4 and run python cachecheck.py log server.log. Since build b9829 (2026-06-28, PR #25078) “forcing full prompt re-processing” and all checkpoint lines are trace level, so at the default -lv 3 the log shows nothing (checked: 0 lines at -lv 3, 1 line at -lv 4 for the same request).

How much is re-processed on each kind of model?

A change inside the conversation costs the tokens after it on full attention, but the whole prompt on SWA and recurrent models when it lies before the last usable checkpoint. What the table shows:

  • Normal multi-turn chat is fine on every kind of model with default settings, because llama-server saves a checkpoint a few tokens before the end of each prompt (4 and 4 + n_ubatch tokens before it, PR #20288). The recurrent model rolled back 4 tokens. With checkpoints off, every turn was a full re-process even though the client changed nothing.
  • The SWA model reused up to 1,404 tokens although its window is 64. The SWA part of the KV cache is n_swa + n_ubatch cells rounded up to 256 (here 64 + 512 → 768, src/llama-kv-cache-iswa.cpp), so a change in roughly the last n_swa + n_ubatch tokens is still cheap. Further back it needs a checkpoint, and there was none before token 898.
  • An early change is the expensive one everywhere. On full attention it costs everything after the change; on SWA and recurrent models it usually costs everything. --swa-full turned the SWA model into the full-attention case (923 instead of 1,821) and did not help the system-prompt change, because nothing after token 45 can be reused on any model.

What about --cache-reuse N? The server disables it at load when the memory cannot be shifted; for SWA models that is the case unless --swa-full is set, because the SWA and full KV caches differ in size (logged as cache_reuse is not supported by this context, it will be disabled; seen with the SWA model). Recurrent memory accepts it. Where it runs, it moves cached chunks of at least N tokens that follow the change, but its loop only skips cached tokens, so it recovers text after a deletion and nothing after an insertion or a replaced word. Measured with --cache-reuse 256: 4 deleted words → cache_n 1,616 instead of 895; 1 replaced word → 898 either way (results_cache_reuse.txt). The shifted chunks keep KV that was computed with the deleted text in front of them, so their output is not identical to a fresh run.

The rule llama-server applies

It reuses the cached tokens up to the first difference only if the memory still holds the state for that position. In server_prompt::get_reuse() (tools/server/server-slot-sched.cpp): let p be the position of the first token to evaluate. The live memory is usable when its smallest kept position is below p (recurrent, hybrid, full attention) or below p − n_swa + 2 (SWA). Otherwise the server looks for the newest checkpoint that ends at or before p and starts early enough, restores it and re-processes from there. If none qualifies, n_past becomes 0 and the message is logged. Checkpoints that cover tokens the new prompt does not share are then erased (“erased invalidated context checkpoint”), which is why one early change also throws away the checkpoints that later turns could have used.

Checkpoints are created before decoding a batch: near the end of each prompt and at batches that start a user message, spaced at least --checkpoint-min-step tokens apart except for the last user message and the prompt end.

cachecheck.py

Download cachecheck.py (MIT, one file, standard library only, ~400 lines). Four commands:

python cachecheck.py diff  A B  --server URL   # A, B: request JSON or --log-prompts-dir .txt; --offline compares characters
python cachecheck.py live  turn1.json turn2.json --server URL   # "{{REPLY}}" in turn2 = turn 1's answer
python cachecheck.py log   server.log            # explains cache lines; start the server with -lv 4
python cachecheck.py gguf  model.gguf            # full attention / SWA / recurrent / hybrid

live exits 0 when the reuse was as good as possible, 1 when the client changed the prefix, 3 for a different slot, 4 for a full server-side re-process and 5 for a large rollback, so it can run in CI against a pinned build.

FAQ

Is “forcing full prompt re-processing due to lack of cache data” a bug?
Usually not. It means the new prompt differs from the cached one at a position the server cannot roll back to and no checkpoint is earlier. In issue #24714 (build 9642) one commenter calls it expected behaviour and others report it as a bug; no maintainer had answered when we read the thread. Find the changed token first.
Why can't I see the message any more?
Since b9829 it is trace level. Use -lv 4, or read timings.cache_n in the response.
Does --swa-full fix it?
For SWA models only, at the cost of a full-size KV cache for the sliding-window layers. It does nothing for hybrid or recurrent models.
My agent (Claude Code, Qwen Code, OpenCode...) triggers it every turn.
Run the server with --log-prompts-dir, take two consecutive prompts and run cachecheck.py diff. If the shared prefix is small, the client puts something variable near the start; if it covers the old prompt, look at slots and checkpoints instead.
Does --cache-reuse help?
Rarely. It is disabled for SWA models without --swa-full, and where it runs it recovers text after a deletion only, not after an insertion or a replaced word.

Limitations

  • Measured on random-weight toy models on CPU at master ab16df3 and build b12733. A real hybrid model (attention + recurrent layers) and real GPU runs were not measured; the hybrid behaviour above is from the source.
  • The DIFFERENT SLOT verdict is covered by unit tests only (test_classify.py); we did not reproduce slot switching with several clients.
  • cachecheck.py reads /slots to see which slot served a turn; with --no-slots that verdict is not available.
  • Multimodal prompts are not handled by diff (images are not text).
