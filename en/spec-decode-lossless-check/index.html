Answers for LLM inference engineers

Is speculative decoding lossless? Why greedy output changes, and a test that tells numerics from bugs

In exact arithmetic, yes: with the standard acceptance rule, speculative decoding returns the same greedy text and samples from the same distribution as the target model alone. On real engines, three things break that. (1) Numerics: the target checks k drafted tokens in one forward pass over k+1 rows, while ordinary decoding runs one row at a time, and the two do not round identically. Where the top two tokens are nearly tied, the choice flips and greedy output diverges from there on. This is expected and not a bug in the acceptance rule. (2) Bugs in the speculative path: open reports in llama.cpp, vLLM and SGLang (table below) show divergence where the baseline's token was a clear winner, or sampled answers that are measurably skewed. (3) Settings that are lossy by design, such as relaxed acceptance thresholds or synthetic acceptance. specdiff.py sends the same prompts to your endpoint with and without speculation and reports which of the three you have.

Why can greedy output differ with speculative decoding on?

Because the verify pass and plain decoding compute the same logits with different kernels or different launch shapes, and greedy decoding turns one flipped near-tie into a different continuation.

  • The acceptance rule itself is exact. At temperature 0 the target accepts a drafted token only if it is the target's own argmax; at temperature > 0 the rejection-sampling rule of Leviathan et al. and Chen et al. keeps the target distribution. Neither depends on how good the draft is: a bad draft costs speed, not quality.
  • The arithmetic is not exact. vLLM's documentation says speculative sampling is "theoretically lossless up to the precision limits of hardware numerics" and that vLLM "does not currently guarantee stable token log probabilities" (vLLM docs, latest). vLLM RFC #54506 isolates the mechanism: the verify pass computes rows with M = k+1, decode with M = 1, and split-K GEMMs and M-dependent reductions give different bits for the same row. In the reporters' workload, that alone dropped acceptance from about 100% to 72%.
  • Quantized targets make it more visible. In llama.cpp #25618, draft-model speculation (DSpark, MTP) diverged from plain decoding on Q4_K_M targets but matched on a bf16 target (Vulkan).
  • Divergence at 100% acceptance is a tell. In llama.cpp #31472, 184 of 184 draft tokens were accepted and the output still differed, so every emitted token came from a multi-token verify batch. Rejections play no part in that.

How do I tell a numerics flip from a real bug?

Look at how far ahead the baseline's token was at the first divergent position. A flip caused by rounding needs a near-tie: the two candidates are within about the size of the numeric noise. A clear winner that gets replaced is a bug in the speculative path, or a lossy setting.

Not always. These options trade the guarantee for speed on purpose. Checked in each project's source on 2026-11-18 (vLLM 92fd8cc, SGLang 21dae9b, llama.cpp 10f173b).

specdiff.py: test your own endpoint

Run the target twice, once without and once with speculation, then point the script at both. It needs nothing beyond Python 3.8. Download specdiff.py.

# vLLM: same model, same flags, only the speculative config differs
vllm serve MODEL --port 8000
vllm serve MODEL --port 8001 --speculative-config '{"method":"ngram","num_speculative_tokens":4,"prompt_lookup_max":4}' \
    --per-request-spec-decode-metrics summary

# SGLang
python -m sglang.launch_server --model-path MODEL --port 30000
python -m sglang.launch_server --model-path MODEL --port 30001 --speculative-algorithm NGRAM

# llama.cpp
llama-server -m target.gguf --port 8080
llama-server -m target.gguf --port 8081 -md draft.gguf --spec-type draft-simple

curl -O https://erimaki-kobo.github.io/en/spec-decode-lossless-check/specdiff.py
python specdiff.py --base http://localhost:8000/v1 --spec http://localhost:8001/v1 --json report.json

What it does:

  1. Greedy test. Eight built-in prompts (or yours with --prompts file.jsonl) at temperature 0, sent twice to the baseline and once to the speculative endpoint, one request at a time so batching stays out of the picture. For each pair it reports the first divergent token, the baseline's logprob gap between its own token and the one the speculative side chose, and the drafted/accepted counts.
  2. Near-tie threshold from your own data. On the tokens both sides agree on, the largest logprob difference is the numeric noise of your stack. A divergence counts as a near-tie when the baseline's gap is at most max(0.05, 4 × that noise) nats, and as large-gap otherwise, including when the other token is not even in the baseline's top-k. Override with --tie-threshold.
  3. Sampling test. 200 samples per endpoint (--samples) at temperature 1 for prompts with short answers of several tokens, then a chi-square test of homogeneity, plus total variation distance as an effect size. The first token comes from prefill on both sides, so the test looks at whole answers, whose later tokens go through verification. Small cells are pooled so the test stays valid. With many distinct answers TV is biased upward even when nothing is wrong; read the p-value.
  4. Did speculation run? Draft and accepted counts come from vLLM's metrics.speculative_decoding (needs --per-request-spec-decode-metrics), SGLang's sglext.spec_tokens_details (the script sends return_spec_tokens_details) and llama-server's timings.draft_n / draft_n_accepted. If nothing was accepted, the verdict is inconclusive.
  5. Bad logprobs are caught. llama.cpp #27972 (open) reports llama-server returning logprob 0.0 with empty top_logprobs for every token when speculation is on. If the speculative side does that, the script warns and classifies from the baseline's logprobs only. Our build at 10f173b returned real logprobs with speculation on.
VerdictExitMeaning
NO_DIFFERENCE_FOUND0Greedy outputs identical, sampled answers consistent, drafts accepted.
SUSPECTED_BUG1A large-gap divergence, or a distribution difference at p < 0.001.

Use --completions for models without a chat template, --extra '{"chat_template_kwargs":{"enable_thinking":false}}' to pass engine-specific fields, --skip-sample for the greedy test only. Both endpoints must serve the same weights; the script cannot check that.

What did the test find on a real engine?

On llama.cpp's CPU backend, draft-model speculation matched plain decoding token for token; n-gram speculation on a Q4_0 target flipped one near-tie; the benchmarking-only synthetic mode skewed the sampled distribution by a wide margin.

Setup: llama.cpp built from 10f173b (2026-11-18), CPU, 1 thread, llama-server with -np 1, /v1/completions. The target is a 4-layer Llama-architecture model with random weights (256 hidden, vocabulary 516, made with make_toy_gguf.py), so the text is nonsense, but every token goes through llama.cpp's real decode and verify kernels. Eight prompts × 256 greedy tokens; sampling: 600 samples per endpoint of 3-token answers for two prompts.

FAQ

Is speculative decoding lossless?
The algorithm is: with the standard acceptance rule, greedy output and the sampling distribution equal the target's. Implementations are lossless only up to floating-point rounding, which can flip near-tied tokens, and only when the speculative path has no bugs and no relaxed settings are on.
Why does my output change at temperature 0 when I turn on speculative decoding?
Most often a near-tie flipped because the verify pass computes several tokens at once with different rounding. Once one token differs, the rest of the greedy continuation differs too. If the baseline's token was clearly ahead at the first difference, suspect a bug instead.
Does n-gram speculation avoid the problem?
Not reliably. It adds no draft model, but the target still verifies in batches. In llama.cpp #25618 n-gram matched plain decoding on a Q4 target; in our CPU run an n-gram setup flipped one near-tie on Q4_0. vLLM #62304 and SGLang #50395 report n-gram-specific problems.
Does a low acceptance rate mean lower quality?
No. Acceptance affects speed only. Quality changes come from numerics, bugs or lossy settings, none of which show up in the acceptance rate.
Can I trust logprobs with speculative decoding on?
Check them. vLLM does not guarantee stable logprobs, and llama.cpp #27972 reports all-zero logprobs from llama-server with speculation. specdiff.py detects the all-zero case.

Limitations

  • The near-tie threshold is a heuristic. A bug can produce a small-gap divergence and pass as numerics; repeated near-tie verdicts on many prompts are still worth a look.
  • top_logprobs are capped (vLLM's default --max-logprobs is 20). If the speculative side's token is not in the baseline's list, the gap is a lower bound and the divergence is classed as large-gap.
  • One request at a time isolates speculation from batching. Production traffic adds batch effects on top; test those separately.
  • The measurements on this page are from a CPU build with a random-weight model. GPU numbers and real models are not measured here.
