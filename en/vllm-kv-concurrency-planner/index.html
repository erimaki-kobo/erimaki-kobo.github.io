Answers for LLM inference engineers

How many concurrent requests fit in vLLM? A KV cache planner that follows vLLM's own startup math

vLLM answers this at startup, and you can compute the same number before you launch. It takes total GPU memory × gpu_memory_utilization, subtracts the weights, the activation peak and its CUDA graph estimate, cuts what is left into blocks of 16 tokens, and logs GPU KV cache size: N tokens, Maximum concurrency for L tokens per request: X.XXx. X is the number of blocks divided by the blocks one request of max_model_len tokens needs. Lowering --max-model-len does not free memory; it only raises X. How many requests really run together is capped separately by --max-num-seqs (256 or 1,024 by default).

The planner below runs that calculation in your browser, from a config.json before launch or from a startup log afterwards. It follows the layer grouping of vLLM v0.33.0, so it also gets models with sliding-window layers right (Gemma 2 and 3, gpt-oss), where "bytes per token × context" overshoots by a factor of two or more.

Which tab? The config tab is exact about the KV side (blocks, groups, what one request reserves) and only as good as your guess for the non-KV memory, which vLLM measures with a profiling pass. Once the server has started, the log tab is exact for both, and it works for every model, including the ones the config tab refuses (Qwen3.5 and other hybrids with linear-attention or Mamba layers, DeepSeek-V4, packed KV formats).

What does vLLM compute at startup?

Seven steps, all visible in the v0.33.0 source. The example is the planner's default: Llama-3.1-8B in bf16 on a 24 GiB GPU.

  1. Budget = ceil(total memory × gpu_memory_utilization). It is a share of the total, not of what is free; if less than the budget is free, startup stops with Free memory on device ... is less than desired GPU memory utilization. The default is 0.92 (worker/utils.py, config/cache.py). Example: 24 × 0.92 = 22.08 GiB.
  2. KV memory = budget − weights − activation peak of a profiling forward pass − the estimated CUDA graph memory. This is the Available KV cache memory line. --kv-cache-memory-bytes sets it directly and ignores the utilization (gpu_worker.py). Example: 22.08 − 14.96 − 1.5 (assumed) = 5.62 GiB.
  3. One page is 16 tokens of one layer: KV heads × (key dims + value dims) × bytes per element × 16. With tensor parallel, each GPU holds max(1, KV heads ÷ TP) heads (kv_cache_interface.py, config/model.py). Example: 8 × 256 × 2 × 16 = 65,536 bytes.
  4. Layers are put into groups that share a block table, and one block holds the pages of the widest group. A model whose layers are all alike is one group (kv_cache_planning.py). Example: 32 layers × 65,536 = 2,097,152 bytes per block, which is 128 KiB per token.
  5. Blocks = KV memory // bytes per block. Example: 2,877 blocks.
  6. Blocks one full-length request needs: ceil(L ÷ 16) for a full-attention group; for a sliding-window group, ceil(min(window − 1 + tokens in flight, L) ÷ 16) + 1, where tokens in flight = concurrent batches (2 with async scheduling, the default) × max_num_batched_tokens. Example at L = 32,768: 2,048 blocks.
  7. Maximum concurrency = blocks ÷ blocks per request, and GPU KV cache size = int(concurrency × L) tokens. One block is the permanently reserved null block: if a single request does not fit in the rest, startup stops and prints an estimated maximum model length. Example: 46,032 tokens, 1.40x at 32,768; 5.62x at 8,192; at 131,072 it refuses to start and estimates 46,016.

How much KV cache does one token take?

It depends on the attention type of each layer, not only on the model size. b is the size of one element: 2 bytes for bf16 or fp16, 1 for fp8.

--kv-cache-dtype auto means "the model's dtype", so a 4-bit AWQ or AutoRound model still gets a 16-bit KV cache. fp8 is opt-in, except for llm-compressor checkpoints that declare a KV cache scheme (attention.py).

Why is "bytes per token × context" wrong for Gemma 3 and gpt-oss?

Because their sliding-window layers do not keep the whole context, and vLLM sizes them by the window. Gemma 3 27B has 62 layers; 52 of them attend to the last 1,024 tokens only. The flat formula gives 496 KiB per token and 62.0 GiB for one 131,072-token request. vLLM instead builds 7 groups (one with the 10 full-attention layers, six with the sliding layers) and reserves:

Gemma 3 27B, bf16 KV, 40 GiB of KV memory, max_model_len 131,072One request reservesMaximum concurrency
Flat formula (every layer keeps every token)62.0 GiB0.65x, "does not fit"
vLLM, max_num_batched_tokens 8,192 (default on GPUs of 70 GiB and more)18.0 GiB2.23x
vLLM, max_num_batched_tokens 2,048 (default below 70 GiB)12.4 GiB3.24x
vLLM with --disable-hybrid-kv-cache-manager (also what a KV connector without hybrid support forces)62.0 GiBrefuses; estimated maximum model length 84,544

Three details move the number. The sliding layers hold window − 1 tokens plus everything the scheduler may have in flight, so a larger --max-num-batched-tokens lowers the concurrency of these models. The 52 sliding layers are split into six groups of at most 10, so vLLM reserves for 60: 8 padding layers, which it also reports in a warning. And every sliding group costs one extra block per request, because a window rarely starts on a block boundary. For gpt-oss-20b the same effect turns 6.0 GiB per 131,072-token request into 3.1 GiB.

A config that sets sliding_window without layer_types makes every layer a sliding-window layer in vLLM. Qwen2 and Qwen3 configs carry a sliding_window value but ignore it unless use_sliding_window is true, so they are plain full attention.

Readings of these numbers that go wrong

Six expectations the startup numbers seem to support, and what vLLM does instead.

ExpectationWhat vLLM does
A smaller --max-model-len uses less GPU memoryThe pool keeps its size; only the concurrency figure changes. A T4 with Llama-3.2-3B logged 5.83, 5.85 and 5.78 GiB of KV cache at 8,192, 4,096 and 16,384 tokens, and 6.66x, 13.37x and 3.30x (forum thread). To use less memory, lower --gpu-memory-utilization or set --kv-cache-memory-bytes.
gpu_memory_utilization is a share of the free memoryIt is a share of the total, for this instance. Two servers on one GPU need shares that add up to less than 1, and each needs its whole share to be free when it starts.
"Maximum concurrency 3.81x" means three requests at mostIt is the count for requests that all reach max_model_len. Blocks are handed out as tokens are processed, so shorter requests share the pool; the cap on running requests is --max-num-seqs. When the pool runs out the scheduler preempts a running request, frees its blocks and recomputes it later (scheduler.py). Watch vllm:kv_cache_usage_perc, vllm:num_preemptions and vllm:num_requests_waiting.
A 4-bit model leaves the saved memory freevLLM still takes its whole budget; what the smaller weights save becomes KV cache. That is why nvidia-smi shows the GPU nearly full for any model.

Everything needed is in config.jsonHub configs leave out keys that equal the class default. Gemma 3 4B's text_config has no head counts (discussion); 8 heads, 4 KV heads and head_dim 256 come from the transformers config class. The planner fills such keys from transformers 5.22.2 and says so under the result.

What are the defaults for max_num_seqs and max_num_batched_tokens?

They depend on the GPU's memory, and on whether you use vllm serve or the LLM class (get_batch_defaults in arg_utils.py, v0.33.0):

GPU memorymax_num_seqsmax_num_batched_tokens, vllm serve / LLM

70 GiB and more, except A100 and GB10 (DGX Spark)1,0248,192 / 16,384

If the planner's "requests held at once" is above max_num_seqs, raise --max-num-seqs to use the memory. If it is below, the KV cache is the limit, and requests beyond it wait or trigger preemption.

Limits

  • No GPU was used. The KV side is checked against vLLM's code and public logs; the non-KV memory (activation peak, CUDA graphs) is your input, because vLLM measures it rather than computes it. Start once, read Available KV cache memory, and put it in the "KV memory" field.
  • The config tab covers full attention, MLA, interleaved and all-sliding window models, tensor parallel and fp8 or 16-bit KV. It refuses models it cannot reproduce instead of guessing. Pipeline parallel, decode context parallel, draft models for speculative decoding and encoder-decoder models are not covered.
  • Models whose vLLM class builds its attention layers differently from the generic rules here (custom sliding-window patterns, KV sharing between layers) can differ. The result table shows the layer counts it assumed; compare them with the model card.
  • Attention backends can raise the block size above 16 for some head sizes. That changes rounding by at most one block per group and request; set "Block size" if your log says otherwise.
  • "Requests held at once" ignores prefix caching, which lets requests with a common prefix share blocks, so real servers often hold more.

Questions

How does vLLM calculate "Maximum concurrency"?

It divides the number of KV cache blocks by the blocks one request of max_model_len tokens needs. The blocks come from the KV memory: total GPU memory times gpu_memory_utilization, minus the weights, the activation peak of a profiling pass and the CUDA graph estimate, cut into blocks of 16 tokens. For a full-attention model one request needs ceil(max_model_len / 16) blocks.

Does lowering --max-model-len reduce vLLM's GPU memory use?

No. vLLM still takes total memory times gpu_memory_utilization and gives everything left after the weights to the KV cache. A shorter max_model_len only means each full-length request needs fewer blocks, so the logged concurrency goes up. To use less memory, lower --gpu-memory-utilization or set --kv-cache-memory-bytes.

Is "Maximum concurrency" the limit on simultaneous requests?

No. It is how many requests fit if every one of them grows to max_model_len. Blocks are handed out as tokens are processed, so shorter requests share the pool and more of them run together, up to --max-num-seqs (256 or 1,024 by default, depending on the GPU). When the pool runs out, the scheduler preempts a running request and recomputes it later.

How much KV cache does one token take in vLLM?

For standard attention: 2 x layers x KV heads x head dimension x bytes per element. Llama-3.1-8B (32 layers, 8 KV heads, 128 dims, 16-bit) takes 128 KiB per token; --kv-cache-dtype fp8 halves it; tensor parallel divides the KV heads per GPU. DeepSeek-style MLA stores one latent vector per layer (kv_lora_rank + qk_rope_head_dim values). Sliding-window layers keep only the window plus the tokens in flight.

Why does vLLM say the model's max seq len needs more KV cache than is available?

One request of max_model_len tokens must fit in the KV cache, with one block held back. If it does not, vLLM stops and prints the estimated maximum model length that would fit. Pass that value (or --max-model-len -1 from v0.14.0) as the context length, raise --gpu-memory-utilization, use --kv-cache-dtype fp8, or spread the model over more GPUs.
