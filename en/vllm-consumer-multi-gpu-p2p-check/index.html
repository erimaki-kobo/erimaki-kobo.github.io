Answers for LLM inference engineers

vLLM hangs with tensor parallel on two GPUs without NVLink: which flag fixes it?

It depends on whether your GPUs have P2P, and whether it actually works. GeForce cards such as the RTX 4090 and 5090 have no P2P with NVIDIA's drivers; vLLM then turns its custom all-reduce off by itself and NCCL uses shared memory, so --disable-custom-all-reduce and NCCL_P2P_DISABLE=1 change nothing. Workstation and data-center cards such as the RTX PRO 6000 do report P2P, and when the IOMMU, ACS or a VM breaks it, both vLLM's custom all-reduce and NCCL's P2P transport can hang: you need both settings, or better, fix the host.

The forum threads mix these cases, which is why the same flag "worked" for one person and "did nothing" for the next. p2pcheck.py tests each path separately, with a timeout, and prints the command line for your machine.

What "No available shared memory broadcast block found in 60 seconds" means

A worker is stuck; the message does not say why. vLLM's main process writes each step into a shared-memory ring buffer that every worker reads. The writer logs this warning when a block has not been read by all workers after 60 seconds (VLLM_RINGBUFFER_WARNING_INTERVAL, default 60), and repeats it every 60 seconds (shm_broadcast.py). The text itself suggests "hanging or doing some time-consuming work (e.g. compilation, weight/kv cache quantization)".

With tensor parallel on PCIe GPUs, the usual stuck point is an all-reduce: one GPU waits for data that the other GPU wrote over a P2P path that does not deliver. That is the case this page is about. If every check below passes, look elsewhere: model loading, torch.compile, or one rank that crashed.

Which all-reduce does vLLM use on your GPUs?

vLLM v0.33.0 has five all-reduce paths for tensor parallel on CUDA. On one node with consumer or workstation GPUs, only two of them can turn on:

So on two PCIe GPUs there are exactly two places a P2P problem can hang vLLM: the custom all-reduce, and NCCL's P2P transport. --disable-custom-all-reduce removes the first, NCCL_P2P_DISABLE=1 the second. The log line Custom allreduce is disabled because your platform lacks GPU P2P capability or P2P test failed means the first was never on.

Check your machine with p2pcheck.py

One Python file, no packages beyond the PyTorch you already run vLLM with. Run it in the same venv or container as vLLM:

curl -O https://erimaki-kobo.github.io/en/vllm-consumer-multi-gpu-p2p-check/p2pcheck.py
python3 p2pcheck.py                    # GPUs 0 and 1
python3 p2pcheck.py --gpus 0,1,2,3     # more GPUs
python3 p2pcheck.py --vllm             # also run vLLM's own TP all-reduce
python3 p2pcheck.py --json report.json --verbose

Each check runs in its own process. A check that does not finish within --timeout seconds (default 60) is killed and reported as HANG, so the script never freezes your shell the way vLLM does.

The script ends with a verdict and a command line, for example:

verdict:
  CAUSE: the driver reports P2P between these GPUs, but a real P2P write or copy failed or hung. vLLM's custom all-reduce and NCCL's P2P transport both use this path, so either one can hang.
    likely why: the GPUs sit in a translated IOMMU domain (type DMA). NVIDIA does not support PCIe P2P with the IOMMU translating on bare metal. Fix: boot with iommu=pt (or turn IOMMU / VT-d off in the BIOS), then rerun this script.
    note: the 1 KiB test vLLM uses (VLLM_SKIP_P2P_CHECK=0) passed, so vLLM's own check would not catch this; only larger transfers fail.

run vLLM as:
  NCCL_P2P_DISABLE=1 vllm serve <model> --tensor-parallel-size 2 --disable-custom-all-reduce

This is the script's verdict for a box where P2P is reported, the 1 KiB IPC test passes, the 64 MiB test and the copy hang, and the GPUs are in a translated IOMMU domain. The per-check lines above the verdict are left out.

How to read the result

peer no, all PASS, NCCL via SHM
Normal for GeForce. Your TP speed is bounded by PCIe through host memory; flags will not make it faster.
peer yes, ipc or copy FAIL / HANG
P2P is advertised but broken. Look at the IOMMU and ACS lines. Fix the host, rerun, and keep the two settings until every check passes.
NCCL defaults HANG, NCCL_P2P_DISABLE=1 PASS
NCCL's P2P transport is the problem. Use NCCL_P2P_DISABLE=1 (and --disable-custom-all-reduce if peer is yes).
Every NCCL run fails
Below vLLM: driver, NCCL build or container. Use --verbose to see the last NCCL lines.
Everything passes but vLLM still hangs
Run with --vllm. If that passes too, the hang is not in the collectives.

What do the workarounds cost?

NCCL_P2P_DISABLE=1 sends NCCL traffic through host memory. One user with two RTX 5090s (patched driver, custom all-reduce off in both runs) measured P2P on versus off at +2.7% mean output throughput over nine single-pass workloads, range −1.9% to +4.7% (forum, 2026-08-11). The cost of --disable-custom-all-reduce on a box where P2P works is not measured here. A box that hangs has no throughput to lose.

What this does not tell you

  • We have not run p2pcheck.py on a dual-GPU machine yet. The parsers, verdict rules and the timeout path are tested without GPUs; the CUDA IPC, copy and NCCL checks follow vLLM's and PyTorch's code but are unverified on real hardware. Reports from your box are welcome.
  • The --vllm check calls vLLM internals that change between releases; it was written against v0.33.0. If it reports "vLLM API may differ", the other checks still stand.
  • Multi-node, NVLink, InfiniBand and ROCm are out of scope.
  • ACS state needs root; without it the script reports "unknown".

Questions

What does "No available shared memory broadcast block found in 60 seconds" mean in vLLM?

It is a symptom, not a cause. vLLM's main process writes each step into a shared-memory ring buffer that every worker reads. The warning is printed when a block has not been read by all workers for 60 seconds, so at least one worker is still stuck in an earlier step. With tensor parallel on PCIe GPUs that worker is usually waiting inside an all-reduce whose data never arrives.

Do RTX 5090 and RTX 4090 support P2P?

Not with NVIDIA's drivers. NVIDIA has said that GeForce cards, including the RTX 40 and 50 series, do not support GPU-to-GPU P2P. On those cards torch.cuda.can_device_access_peer returns False, vLLM turns custom all-reduce off by itself, and NCCL moves data through shared host memory. That is slower than P2P but it is not a bug.

Should I use --disable-custom-all-reduce or NCCL_P2P_DISABLE=1?

They turn off different things. --disable-custom-all-reduce stops vLLM's own all-reduce kernel, which needs working P2P between the GPUs. NCCL_P2P_DISABLE=1 stops NCCL's P2P transport, so NCCL uses shared memory instead. If the driver reports P2P but P2P does not actually work (often an IOMMU in translated mode), both paths can hang and you need both settings. If the GPUs report no P2P, neither changes anything except silencing a warning.

Does iommu=pt fix vLLM hangs on multiple GPUs?

It fixes one cause: GPUs that support P2P but sit behind an IOMMU in translated (DMA) mode on bare metal. NVIDIA does not support PCIe P2P with IOMMU translation, and the transfers can hang or corrupt data. Booting with iommu=pt puts devices in passthrough mode. It does not help on GeForce cards without P2P, in virtual machines, or when the cause is ACS or a driver bug.

What does NCCL WARN Cuda failure 217 'peer access is not supported between these two devices' mean?

On PCIe GPUs without P2P, drivers in the 560 to 575 branches had a bug in host memory sharing through cuMem that NCCL uses for its shared-memory transport. NVIDIA fixed it in the r580 drivers. Upgrade the driver, or set NCCL_CUMEM_HOST_ENABLE=0.
