vLLM returns the tool call in content, or tool_calls is empty: what each --tool-call-parser does with the same model output, v0.15 to v0.34, and a script to test your server

For a well-formed call, every tool parser tested returns the right tool_calls in every release from v0.15.1 to v0.34.0 (gemma4 from v0.19.1), streaming included. The failures come from four places, each measured below on vLLM's own parser code: (1) a --tool-call-parser that does not match the model's call format leaves the markup in content, or drops the call so the answer is empty (qwen3_xml reading a JSON call in every release, qwen3_coder from v0.24.0); (2) llama3_json and pythonic only read a call at the start of the output, so any text before it puts the whole call in content; (3) with --reasoning-parser qwen3, a call written inside the thinking block stays in reasoning (fixed for an unclosed block in v0.20, for a closed one in v0.24); (4) a call cut by max_tokens comes back as a complete-looking call with keys missing, and before v0.33.0 with finish_reason: "tool_calls".

How do I test my own server?

toolcheck.py sends five tool requests (auto, required, two calls, an object argument with non-ASCII text, and one cut by max_tokens), each with and without streaming, and labels every answer. It works with any OpenAI-compatible server and needs only Python 3.8+.

python3 toolcheck.py --base-url http://localhost:8000/v1 --model Qwen/Qwen3-8B
python3 toolcheck.py --base-url http://localhost:8000/v1 --model M --extra '{"chat_template_kwargs": {"enable_thinking": false}}'

Labels: ok, markup_in_content, call_in_reasoning, empty, no_call (the model chose not to call), bad_json, schema_mismatch, stream_header (a call's first chunk lacks id or name), stream_differs, finish_reason, http_<status>. The exit code is 1 when an answer points at the server rather than the model. Checked two ways: against a local server that replays what each release's parsers returned above (1,960 of 1,960 labels match this page's verdicts), and against a running llama-server (build 12733) with a small test model.

How was this measured?

The vllm/ source of each of 20 releases (the newest patch of every minor from v0.15.1 to v0.34.0, from vLLM's git tags) was loaded in Python 3.12 without a GPU: torch, the compiled extension and the model and engine code were replaced by stubs, and the tool parsers, reasoning parsers and request models ran as released. Each parser was built as vLLM's chat server builds it (parser(tokenizer, request.tools)) and given the same model outputs through extract_tool_calls and, piece by piece, extract_tool_calls_streaming. The streamed pieces were put back together the way an OpenAI client does.

The tokenizer is a stand-in, as in vLLM's own parser tests: each special token (<tool_call>, <|tool_call>, <think>, ...) is one token, and other text is split into words, spaces and single characters. A real tokenizer cuts text differently, so a streaming result here holds for this split; the non-streaming results do not depend on it. Not covered: mistral (needs the Mistral tokenizer), openai/gpt-oss (Harmony format), and the server's own code around the parser, except the reasoning chain and the finish_reason rule, which were read from each release's source.

Questions

Why does vLLM return the tool call in content with tool_calls empty?

The tool parser did not recognise the model's output. Either --tool-call-parser does not match the model's call format (hermes reads JSON inside <tool_call>, qwen3_coder reads <function=...> inside <tool_call>, gemma4 reads <|tool_call>call:...; a mismatch leaves the markup in content), or the model wrote text before the call and the parser is llama3_json or pythonic, which only read a call at the very start of the output (every release from v0.15.1 to v0.34.0). The server still answers 200 with finish_reason stop.

Why is tool_calls empty and content empty, with the call in reasoning (Qwen3, Qwen3.5)?

The qwen3 reasoning parser kept the call in reasoning, and the tool parser only reads content. Measured on vLLM's own parser code: a call written before </think> (no </think> at all) stays in reasoning in v0.17.1 to v0.19.1 and comes out from v0.20.2 (PR #35687, in v0.20.0); a whole call inside a closed <think>...</think> block stays in reasoning in every release up to v0.23.0 and comes out from v0.24.0. On an older release, turn thinking off for tool turns (chat_template_kwargs enable_thinking false) or upgrade.

Why is the answer completely empty (no content, no tool_calls, no reasoning)?

qwen3_xml in every release, and qwen3_coder and glm45 from v0.24.0, consume a <tool_call> section they cannot read: a JSON call inside <tool_call> (the hermes format, written by Qwen2.5, Qwen3 and many fine-tunes) disappears instead of landing in content. Use --tool-call-parser hermes for those models; qwen3_coder is for models that write <function=name><parameter=...>.

Why does a tool call come back with arguments missing?

max_tokens cut the model's output inside the call. In v0.34.0, qwen3_coder, qwen3_xml, glm45, minimax_m2 and gemma4 return the cut call as a complete call with valid JSON arguments (the keys after the cut are simply missing). Before v0.33.0 vLLM also reports finish_reason "tool_calls" for it; from v0.33.0 (PR #59324) finish_reason stays "length". Check finish_reason before running a call, and raise max_tokens.

What does "auto" tool choice requires --enable-auto-tool-choice and --tool-call-parser to be set mean?

vLLM answers HTTP 400 with that text when a request has tools and tool_choice auto (the default when tools are sent) but the server was started without both flags. The same text is in every release from v0.15.1 to v0.34.0. Start vllm serve with --enable-auto-tool-choice --tool-call-parser <name>.

How do I test my own server?

Run toolcheck.py (Python 3.8+, no packages): python3 toolcheck.py --base-url http://localhost:8000/v1 --model <name>. It sends five tool requests with and without streaming and labels each answer (ok, call left in content, call in reasoning, empty, invalid JSON, schema mismatch, missing stream header, finish_reason). Run it more than once: the model decides whether to call.
