Answers for LLM inference engineers

ImportError: cannot import name 'X' from 'vllm...' (GuidedDecodingParams, get_open_port, ChatCompletionRequest, ...): which vLLM releases have it

Most of these errors come from three vLLM releases. 0.12.0 (2025-12-03) removed GuidedDecodingParams (use StructuredOutputsParams, from 0.11.0) and split vllm.utils into submodules: get_open_port and get_ip are in vllm.utils.network_utils, FlexibleArgumentParser in vllm.utils.argparse_utils, get_tokenizer in vllm.tokenizers. 0.14.0 (2026-01-20) dropped the last deprecated alias, vllm.utils.get_open_port. 0.15.0 (2026-01-29) split vllm.entrypoints.openai.protocol by endpoint. The import is often not in your code but in TRL: TRL before 0.27.0 needs vLLM below 0.12.0, and trl vllm-serve before TRL 0.28.0 needs vLLM below 0.14.0. For any other name, in any module of vLLM, paste the error below.

The TRL release decides which vLLM names are imported. These ranges come from TRL's source at every release from 0.14.0 to 1.18.2.

How do I read the error?

  • The file in the traceback tells you whose import it is. trl/trainer/grpo_trainer.py or trl/scripts/vllm_serve.py means TRL; fix it with the TRL table above, not in your code.
  • A DeprecationWarning like "vllm.utils.get_open_port is deprecated and will be removed in a future version" (vLLM 0.12 and 0.13) is the last release before the import fails.
  • Patch releases: vLLM 0.11.1 and 0.11.2 already shipped some of the 0.12.0 submodules, such as vllm.utils.network_utils. This page reads the first release of each minor version, so it says "from 0.12.0".

How was this read, and how was it checked?

From the source of each release tag, with Python's ast module; no release was installed or imported. A module's names are everything it binds at module level, what from .x import * brings in, and the names a module-level __getattr__ serves from a table of strings (the lazy top level of vllm, the deprecated aliases of vllm.utils in 0.12 and 0.13, the lazy config and processor classes of vllm.transformers_utils). Code under if TYPE_CHECKING: is skipped. Dates come from PyPI. The TRL column was read from TRL's release tags the same way.

Checks: (1) each of the 115 top-level names is found as plain text in vllm/__init__.py in every release of its range (2,512 name-and-release pairs) and not on either side (30 edges). (2) A regular expression finds 206,105 definitions in 22,937 file versions; all are among the names read. (3) Against a different source, the wheels on PyPI (read by HTTP range requests), 18 release checks agree:

Limits

  • Nothing was installed or run. "Has it" means the import statement resolves in the source; an import can still fail at run time for another reason (a missing CUDA library, a compiled extension built for a different PyTorch).
  • Only the first release of each minor version was read (and the newest). A change in a patch release is attributed to the next minor.
  • Names a module serves through a __getattr__ that computes them, rather than looking them up in a table, are not counted.

Questions

How do I fix "cannot import name 'GuidedDecodingParams' from 'vllm.sampling_params'"?

vLLM 0.12.0 (2025-12-03) removed GuidedDecodingParams; 0.11.2 is the last release with it. Its replacement, StructuredOutputsParams, exists from 0.11.0. If the import is in TRL (GRPOTrainer, RLOOTrainer, OnlineDPOTrainer or trl vllm-serve), upgrade TRL to 0.27.0 or later, which picks the class by vLLM version, or keep vLLM below 0.12.0.

How do I fix "cannot import name 'get_open_port' from 'vllm.utils'"?

Import it from vllm.utils.network_utils (from 0.12.0). vLLM 0.12 and 0.13 still served the old import with a DeprecationWarning; 0.14.0 (2026-01-20) removed it. trl vllm-serve before TRL 0.28.0 uses the old import, so upgrade TRL or keep vLLM below 0.14.0.

Where did vllm.entrypoints.openai.protocol go?

vLLM 0.15.0 (2026-01-29) split it by endpoint: ChatCompletionRequest is in vllm.entrypoints.openai.chat_completion.protocol, CompletionRequest in vllm.entrypoints.openai.completion.protocol, and ErrorResponse in vllm.entrypoints.serve.engine.protocol from 0.29.0. 0.14.1 is the last release with the old module.

Why do so many vllm.utils imports fail after upgrading to vLLM 0.12?

0.12.0 split vllm.utils into submodules (network_utils, argparse_utils, math_utils, torch_utils, mem_utils and others) and moved get_tokenizer to vllm.tokenizers. Only three names kept a deprecated alias. The lookup shows the new module for each name.

Does this page cover the model and layer modules too?

Yes: every module of vllm from 0.1.0 to 0.34.0, 122,592 module-and-name pairs in 4,336 modules, read at the first release of each minor version.
