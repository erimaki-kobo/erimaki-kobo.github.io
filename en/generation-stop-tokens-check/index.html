Answers for LLM inference engineers

Why does my model not stop generating? The end-of-turn token, and which engines stop on it

A chat model ends its answer with one special token, written by its chat template: <|eot_id|> for Llama 3, <|im_end|> for Qwen, <end_of_turn> for Gemma 2 and 3, <turn|> for Gemma 4. Generation stops only if the engine counts that token as an end token, and each engine builds that set from different files. Transformers reads generation_config.json, vLLM adds the tokenizer's eos_token, llama.cpp reads the GGUF and a list of 24 built-in token texts, and Ollama adds the Modelfile's stop strings. Paste a model's files below to see where each engine stops.

How was this built?

  • Engine rules: read from generation/utils.py and generation/configuration_utils.py (Transformers v5.22.2), sampling_params.py, v1/engine/input_processor.py and transformers_utils/config.py (vLLM v0.33.0), configs/model_config.py, managers/schedule_batch.py and utils/hf_transformers/common.py (SGLang v0.5.23), utils.py and tokenizer_utils.py (MLX-LM v0.32.2), src/llama-vocab.cpp and gguf-py/gguf/vocab.py (llama.cpp b12352), llm/llama_server.go (Ollama v0.40.16).
  • llama.cpp lists: the token texts compared in src/llama-vocab.cpp at b12352, extracted by a script; the first build for each by binary search over the release tags.
  • Predicted GGUF ids: without a load log, the checker takes the eos the converter would write (tokenizer_config.json's eos_token, else config.json's eos_token_id). Some converters set eot or eom as well, which only adds tokens.
  • Templates: llama.cpp's models/templates at b12352, rendered with @huggingface/jinja 0.5.13.

What this page does not cover

  • No model was run. The checker reports which tokens each engine treats as the end; whether the model emits that token is up to its weights.
  • Stop strings in requests (stop) are matched on text and work in every engine; they are not part of the table.
  • Older releases of Transformers, vLLM, SGLang and MLX-LM may differ; vLLM began reading eos_token_id from generation_config.json in v0.4.1 (2024-04).
  • Ollama's MLX runner on macOS and its older own engine (0.5.12 to 0.31.1) are not covered.

Questions

Why does Llama 3 Instruct keep generating after <|eot_id|>?
Its tokenizer's eos_token is <|end_of_text|>, while a chat turn ends with <|eot_id|>. The second one is only listed in generation_config.json (eos_token_id [128001, 128009]). An engine or copy of the model that does not read that list stops only at <|end_of_text|>, which the model rarely emits in chat. vLLM reads it from v0.4.1.
Which file decides where generation stops?
It depends on the engine. Transformers' generate() uses generation_config.json (or config.json when that file is missing) and ignores the tokenizer's eos_token. vLLM adds the tokenizer's eos_token to that. SGLang adds config.json as well. llama.cpp uses the eos, eot and eom ids stored in the GGUF plus a built-in list of token texts. Ollama passes stop strings from the Modelfile to llama.cpp.
How do I make vLLM stop on a token?
Send "stop_token_ids": [ID] in the request, or start vLLM with --generation-config pointing at a directory whose generation_config.json lists the id in eos_token_id.
How do I make llama.cpp or Ollama stop on a token?
For llama.cpp, --override-kv tokenizer.ggml.eos_token_id=int:ID makes that token the eos, and the eos is always in the end-of-generation set. For Ollama, add PARAMETER stop "<token>" to the Modelfile and run ollama create.
My fine-tuned model never stops, but the base model does. Why?
If the training examples did not end with the end-of-turn or eos token, the model never learned to emit it. No engine setting fixes that; add the token to the end of every training example and train again.
